## Context

Как Fyne 2.8.0 выдаёт кадры (проверено по исходникам модуля):

- **Android.**
  - Цикл драйвера (`internal/driver/mobile/driver.go:213`) по таймеру `time.NewTicker(time.Second / 60)` шлёт `paint.Event`. `handlePaint` вызывает `TickAnimations()` и рисует, если холст грязный.
  - `publish` уходит в поток `mainUI` (`mobile/app/android.go:440`), там `eglSwapBuffers` («blocks until vsync», строка 510).
  - Касания читает отдельный поток с `ALooper` (`runInputQueue`, строка 524) и сразу передаёт их в цикл как `touch.Event`, без времени события.
- **ПК.**
  - Цикл (`glfw/loop.go:132`) по таймеру 60 Гц опрашивает события, вызывает `TickAnimations()` и `drawSingleFrame()`.
  - `SwapInterval` задаётся только на Wayland (`window_desktop.go:841`), на Windows действует значение драйвера.
- **Анимации.** `internal/animation/runner.go` берёт `time.Now()` в момент такта.
- **Наш замер.** `frameprobe` считает интервалы между тактами анимации, то есть шаг таймера. Когда кадр реально показан, он не видит.

Отсюда рывки. Таймер 60 Гц и vsync экрана (120 Гц на телефоне, 160 Гц на ПК) не синхронны, поэтому кадр показывается то через 1, то через 2–3 vsync. При частоте 60 на 60 фаза таймера уплывает, и кадры время от времени пропускаются. Шаг анимации считается от `time.Now()`, а не от момента показа, поэтому сдвиг за кадр тоже неровный.

Ограничения:
- minSdk 30: `AChoreographer_postFrameCallback64` (API 29), `AChoreographer_registerRefreshRateCallback` и `ANativeWindow_setFrameRate` (API 30) доступны из C без Java;
- сборки только для Windows и Android;
- одно главное окно; окно браузера на ПК — Firefox, не Fyne.

## Goals / Non-Goals

**Goals:**
- замер показа кадров: сначала «до», потом «после»;
- один кадр на vsync во время движения при любой частоте экрана (60–500 Гц, адаптивной тоже);
- ни одного кадра в простое;
- ровный шаг анимаций и прокрутки;
- кадры смены вкладок не длиннее 50 мс;
- минимальный, описанный патч Fyne.

**Non-Goals:**
- инерционная прокрутка;
- PR в Fyne и обновление Fyne;
- Vulkan;
- Linux/Wayland (поведение Fyne не меняется);
- браузер.

## Decisions

### D1. Копия Fyne в `third_party/fyne`

- **Копия.** Модуль `fyne.io/fyne/v2@v2.8.0` копируется из кэша модулей целиком, с `LICENSE`, в `third_party/fyne`. В `go.mod` добавляется `replace fyne.io/fyne/v2 => ./third_party/fyne`, `require` остаётся `v2.8.0`.
- **Отдельный модуль.** У копии свой `go.mod`, поэтому `go vet ./...` и `go test ./...` корня её не обходят.
- **`third_party/fyne/PATCHES.md`.** Версия-основа, затем по каждой правке: файл, что изменено, зачем, как перенести. Каждая правка в коде помечена комментарием `// mangareader:`, их можно найти поиском.
- **Тест.** Проверяет, что `replace` указывает на копию, а версия в `third_party/fyne/PATCHES.md` совпадает с `require`. Иначе после `go get` можно молча получить исходный Fyne.
- **`THIRD_PARTY_NOTICES.md`.** В строке `fyne.io/fyne/v2` пометка «modified copy in `third_party/fyne`, see PATCHES.md». Лицензия та же, BSD-3-Clause.

Альтернативы: форк на GitHub (нужна сеть и внешний репозиторий) и `.patch`, накладываемые при сборке (сложнее сборка). Отклонены в grill-сессии.

### D2. Пакет `fyne.io/fyne/v2/driver/pacing` (добавлен в копию)

Единственная точка связи нашего кода с темпом кадров:

```go
type Frame struct {
    Time    time.Time     // vsync, к которому готовится кадр (время анимаций)
    Period  time.Duration // период vsync сейчас
    Swapped time.Time     // после SwapBuffers
    Present time.Time     // фактический показ, если известен (Android, EGL), иначе ноль
}
func FrameTime() time.Time            // время текущего кадра; вне кадра — time.Now()
func RefreshRate() float64            // частота экрана/монитора окна, Гц
func Mode() string                    // "choreographer", "vsync", "dwm", "timer"
func PresentSource() string           // "egl", "swap", "dwm"
func SetObserver(func(Frame))         // замер; вызывается в UI-потоке после кадра
func SetRateHint(rate float64)        // Android: частота на время движения, 0 — не просить (D5)
```

`SetObserver` и `SetRateHint` вызываются из UI-потока. Пакет не импортирует виджеты.

Без тега `android` и `windows` (то есть Linux) пакет возвращает `time.Now()`, частоту 60 и `Mode() = "timer"`. Наблюдатель там вызывается после каждого кадра старого цикла.

### D3. Замер показа кадров (первым, до патча темпа)

Первая сборка «до» уже идёт на копии Fyne. В ней есть `pacing` с наблюдателем, но цикл драйвера старый (таймер 60 Гц).

- **Сетка vsync.**
  - **Android.** Отдельный кадровый колбэк `AChoreographer` на потоке ввода (у него уже есть `ALooper`) записывает метки vsync, а `registerRefreshRateCallback` даёт период.
  - **Время показа на Android.** Если поддерживается `EGL_ANDROID_get_frame_timestamps`, берётся `EGL_DISPLAY_PRESENT_TIME_ANDROID` (точное время показа, приходит с задержкой в 2–3 кадра). Иначе время после `eglSwapBuffers`, привязанное к ближайшему следующему vsync.
  - **ПК.** `DwmGetCompositionTimingInfo(NULL)` даёт `qpcVBlank` и `qpcRefreshPeriod`. Кадр считается показанным на первом vblank после возврата `SwapBuffers`.
- **Сводка** (`frameprobe`, чистые функции с тестами):
  - `k` — число vsync между соседними показанными кадрами;
  - `1v` — доля кадров с `k = 1`;
  - `miss` — Σ(k−1) / Σk. Промежутки `k > 8` считаются простоем и в сводку не входят;
  - `dy` — неровность скорости прокрутки: v = сдвиг / k (за vsync), dy = Σ|v[i] − (v[i−1] + v[i+1])/2| / Σ|v[i]| по тройкам соседних кадров одного направления без простоя. Смещение сетки или ленты драйвер записывает в `Frame.Sample` в момент рисования кадра (`SetSampler`). Первая версия — коэффициент вариации сдвига, считанного в наблюдателе, — оказалась непригодной, см. «После отчёта с телефона».

  Прежние поля (`p50`, `p95`, `max`, `slow`, `gc`, `heap`) остаются. Теперь они считаются по интервалам показа, а не тактов.
- **Шапка отчёта:** `refresh` (Гц), `pacing` (`Mode()`), `present` (`egl` / `swap` / `dwm`).
- **Критерий готовности:** на телефоне пользователя (120 Гц, «Ограничить 60 Гц» выключено) в сценариях `grid` и `strip` `1v ≥ 95%` и `miss < 2%`, на ПК 160 Гц то же. Плюс собственный тест пользователя.

### D4. Android: кадры по `AChoreographer`

- **Колбэк.** Таймер в цикле драйвера заменяется каналом `vsync`. Колбэк `AChoreographer_postFrameCallback64` живёт на потоке ввода (`runInputQueue`, `ALooper` уже есть) и кладёт в канал метку кадра. Если канал полон, метка заменяется.
- **Цикл.** По метке цикл ставит `pacing.FrameTime`, вызывает `TickAnimations()` и рисует, если холст грязный. `publish` → `eglSwapBuffers` как раньше.
- **Когда нужен кадр** (`wantFrame`):
  - холст грязный;
  - идут анимации;
  - палец на экране;
  - выполнилась функция `fyne.Do`;
  - пришло событие размера или жизненного цикла.

  Колбэк заказывается на следующий vsync, только пока `wantFrame` или ещё 4 кадра после последнего нарисованного (хвост для отложенных обновлений). Иначе не заказывается, и кадров нет. Любое событие или `fyne.Do` заказывает его снова.
- **Частота.** `registerRefreshRateCallback` обновляет `Period` и `RefreshRate()`. Адаптивные экраны (LTPO) меняют частоту сами, колбэк идёт по их vsync.
- **Фон.** При уходе в фон (окно уничтожено) колбэки не заказываются. При возврате — как при запуске.

Альтернатива: таймер с частотой экрана, прочитанной при запуске. Отклонена: фаза уплывает относительно vsync, а адаптивную частоту таймер не отследит.

Поток: колбэк Choreographer работает на потоке ввода (C), в Go попадает через канал. Состояние драйвера меняет только цикл драйвера, то есть UI-поток Fyne.

### D5. Android: запрос частоты на время движения

Пока `SetRateHint(maxRate)` с `maxRate > 0` и идёт движение, на `ANativeWindow` окна ставится `ANativeWindow_setFrameRate(w, maxRate, ANATIVEWINDOW_FRAME_RATE_COMPATIBILITY_DEFAULT)` (вызов — на потоке GL, где окно точно живо). `maxRate` — наибольшая частота режимов с текущим разрешением, её даёт `DisplayRate.kt` через `internal/display`; поэтому `SetRateHint` принимает частоту, а не флаг из D2: из NDK режимы дисплея не узнать. Через 500 мс без движения ставится `0` («решает система»).

Движение для запроса частоты — палец на экране или анимация, которая перерисовывает холст на каждом vsync не меньше 200 мс. Просто «идут анимации» не годится: фокус в поле ввода запускает бесконечное мигание курсора Fyne (затухание по 100 мс), и частота держалась бы максимальной всё время, пока поле в фокусе (видно на эмуляторе: `requestedFrameRate` не снимался).

`internal/display` при запуске и при смене настройки вызывает `SetRateHint(maxRate)`, если «Ограничить 60 Гц» выключено, и `SetRateHint(0)`, если включено. Если включено «Ограничить 60 Гц», запроса нет, и режим 60 Гц из `DisplayRate.kt` остаётся как сейчас. Ошибка вызова пишется в журнал один раз.

### D6. Android: касания по кадрам (по замеру «до»)

Делается, если в отчёте «до» у ручного замера `dy` заметно выше, чем у автопрокрутки.

- В копии драйвера `touch.Event` получает время (`AMotionEvent_getEventTime`, а для пакетных точек — `getHistoricalEventTime`).
- `TypeMove` одной последовательности копятся до кадра. В начале кадра в цикл уходит одно движение, пересчитанное на `метка vsync Choreographer − 5 мс` (не `FrameTime` — тот на период позже: к началу кадра новее точек ещё нет, и положение всегда экстраполировалось бы; так было в первой сборке, ручной `dy` 1,0): интерполяция между двумя окружающими точками, а если новее точки нет, экстраполяция не дальше 8 мс от последней (как `InputConsumer` в Android).
- `TypeBegin` и `TypeEnd` передаются сразу, перед `TypeEnd` уходит накопленное движение.

Если замер покажет, что это не нужно, требование «Касания по кадрам» убирается из спецификации, а пункт закрывается с пометкой.

### D7. ПК: vsync

- **Темп.** После создания контекста окна — `glfw.SwapInterval(1)` (не на Wayland: там остаётся 0, как в Fyne). Таймер цикла идёт с периодом `1/(1,1 × частота монитора)`, то есть чуть чаще vsync. Канал тикера в Go буферизован на одно значение, поэтому пока `SwapBuffers` ждёт vsync, лишние такты не копятся. После возврата такт уже ждёт, кадр рисуется сразу, и цикл сам держится на vsync.
- **Простой.** Если кадр не рисовался 250 мс, период таймера 1/60 с: события опрашиваются, кадров нет. Первое событие или `fyne.Do` возвращает быстрый период.
- **Частота монитора.** Берётся у монитора, на котором центр окна (`glfw` `GetVideoMode().RefreshRate`). Обновляется при перемещении окна и изменении конфигурации мониторов.
- **vsync выключен в драйвере.** Если 30 кадров подряд `SwapBuffers` возвращается быстрее, чем за 0,5 периода, кадры шли один за другим и в среднем чаще 0,95 периода, vsync считается выключенным. Последнее условие нужно, потому что короткий `SwapBuffers` бывает и с vsync (очередь кадров драйвера, тяжёлые кадры на 160 Гц), а кадры чаще vsync — нет. После этого кадр после `SwapBuffers` ждёт ближайшей композиции DWM (`DwmFlush`, она идёт по vblank), таймер цикла прежний (1,1 × частота), `Mode() = "dwm"`. Без DWM — таймер с частотой монитора, `Mode() = "timer"`. В журнал пишется строка. Проверка повторяется при смене монитора.

  Сначала был таймер с частотой монитора, как в первой версии решения. Замер с имитацией (`SwapInterval(0)`): процессор 15,6 с против 7,4 с с vsync на тех же сценариях, а `1v` в `search` 82%, потому что таймер биением уходит от vblank. С `DwmFlush` — 7,1 с и `1v` 99,6%.
- **Время кадра.** `FrameTime` — vblank DWM, на котором кадр будет показан: первый после `now + P/2`. Такт начинается сразу после `SwapBuffers`, у самой границы vblank, и без сдвига время кадра прыгало бы на соседний vblank (на замере `dy` 0,12 вместо 0,07). Без DWM — время такта.
- **Время показа в замере.** Первый vblank DWM после начала `SwapBuffers`, а не после возврата: блокирующий `SwapBuffers` возвращается у самой границы vblank, и оценка по возврату давала пары `k = 0` / `k = 2` (на замере `miss` 2,1% вместо 0,3%). На Android без меток EGL так же: от начала `eglSwapBuffers`.

### D8. Время анимаций

- `internal/animation/runner.go` берёт время такта из `pacing.FrameTime()` вместо `time.Now()`.
- Наш код с бюджетами и плавным движением переходит на `pacing.FrameTime()`: `coverPresenter`, `warmer`, сглаживание колеса, автопрокрутка `probe_on.go`.
- `fyne.Animation` с прогрессом от времени и так получает ровный шаг.

### D9. Смена вкладок

Сценарий `tabs` в замере «до» даёт `max`. Для диагностики `probe_on.go` на время сценария меряет внутри кадра отдельно `TickAnimations`, раскладку и рисование. В отчёт это не идёт, только в журнал.

Правка по результату:
- если дорого построение или раскладка вкладки — вкладка строится один раз и дальше только показывается и скрывается;
- если дорого GPU (обложки) — первый кадр вкладки без новых текстур, текстуры по бюджету `coverPresenter`.

Цель — `max` не больше 50 мс в сценарии `tabs` на телефоне и ПК.

## Risks / Trade-offs

- **[Обновление Fyne теперь ручное]** → `PATCHES.md`, пометки `// mangareader:` и тест на `replace` с версией.
- **[Прошивка игнорирует `setFrameRate`, приложение остаётся на 60 Гц]** → темп всё равно по vsync, рывков нет, просто 60 кадров. В шапке отчёта видна фактическая частота.
- **[`EGL_ANDROID_get_frame_timestamps` есть не везде]** → запасной вариант: swap плюс сетка vsync. В шапке видно, какой источник использован.
- **[vsync на ПК блокирует цикл, и `fyne.Do` ждёт до одного периода]** → при 60–500 Гц это 2–17 мс, как и сейчас с таймером.
- **[Перетаскивание окна на Windows блокирует цикл (модальный цикл Win32)]** → так и сейчас, поведение не меняется.
- **[Батарея: 120 кадров в секунду при движении]** → кадры только при движении, в простое ноль. «Ограничить 60 Гц» остаётся.
- **[Интерполяция касаний добавляет ~5 мс задержки]** → делается только по замеру. Задержка меньше одного кадра 120 Гц.
- **[Колбэк Choreographer на потоке ввода задерживается обработкой касаний]** → обработка касаний короткая (передача в канал). Если замер покажет задержки, колбэк уходит на отдельный поток с `ALooper`.

## Замеры

Как снимаются: во время замера пробник помечает холст грязным на каждом такте, поэтому кадр рисуется на каждом такте цикла, как при прокрутке. Интервалы — между показами кадров (`Frame.Present`), `k` — число vsync между показами.

### «До» (копия Fyne, `pacing` с наблюдателем, цикл драйвера прежний)

**ПК**: монитор 160 Гц, окно 960×640, масштаб 1,5, 199 галерей, `refresh: 160 Hz`, `pacing: timer`, `present: dwm`. Отчёт: `perf-20261103-193905.txt`.

**Эмулятор** (x86_64, Android 15, один режим 60 Гц, программный GL, 199 галерей, «Ограничить 60 Гц» вкл.): `refresh: 60 Hz`, `pacing: timer`, `present: swap` (меток EGL нет). ### Android на эмуляторе после D4–D5 (3.4)

- **Частота выше 60 Гц на эмуляторе** недоступна: у дисплея AVD один режим 60 Гц. Проверяется только 60 Гц.
- **Простой:** по `dumpsys SurfaceFlinger --latency` за 6 с без касаний ни одного кадра; первое касание запускает кадры.
- **Фон и возврат, поворот:** окно рисуется, прокрутка работает, ошибок в журнале нет.
- **Запрос частоты:** с выключенным «Ограничить 60 Гц» во время свайпа у слоя приложения `requestedFrameRate 60.00 Hz Default` (наибольший режим эмулятора), через 2 с после — запроса нет; с полем ввода в фокусе (мигает курсор) — нет; с включённым — только режим окна от `DisplayRate.kt` (`Exact`), наш запрос не идёт.
- **Сценарии** (`pacing: choreographer`): сетки по-прежнему упираются в программную отрисовку (p50 50–83 мс). `paged` `1v` 81,6% (как «до»), `strip` `1v` 64,9% против 84,0% «до». Кадр ленты на эмуляторе рисуется 13–16 мс при периоде 16,7 мс: таймер начинал кадры в любой фазе, и очередь буферов SurfaceFlinger сглаживала опоздания ценой задержки, а по Choreographer кадр начинается на vsync и должен успеть к следующему (как у обычных приложений Android). Для телефона, где кадр рисуется за единицы миллисекунд, это не помеха; критерий проверяется отчётом с телефона.

### Смена вкладок (7.1–7.2)

Диагностика: на время сценария `tabs` пробник пишет в журнал, сколько занял `SelectIndex` и сколько прошло от него до `SwapBuffers` кадра с новой вкладкой.

- **До правки.** ПК: `SelectIndex` 4–7,5 мс, до `SwapBuffers` 2,5–5 мс. Эмулятор: `SelectIndex` 50–100 мс (вкладка «Настройки» — до 100), до `SwapBuffers` 87–158 мс.
- **Причина** (профиль `SelectIndex` в тесте оболочки на 200 галерей). `AppTabs` при каждом выборе вызывает `Refresh`, а `baseTabsRenderer.applyTheme` — `Refresh` содержимого **всех** вкладок. `Container.Refresh` освобождает текстуры всех изображений внутри, поэтому видимые обложки загружались в GPU заново. Кроме того, `Show` содержимого-виджета (прокрутки) обновляет всё его дерево (карточки настроек, переключатели, подписи).
- **Правка** — по D9 «первый кадр без новых текстур», построение вкладок не менялось.
  - В копии Fyne (`container/tabs.go`) содержимое вкладок обновляется только при смене темы.
  - В `shell.go` содержимое каждой вкладки лежит в простом контейнере (`tabContent`): `Show` контейнера только снимает флаг.
  - Тесты: Fyne-тест `TestAppTabsSelectKeepsContent` (без правки падает) и тест оболочки `TestTabContentIsPlainContainer`. `SelectIndex` в тесте оболочки: 2,3–3,7 мс → 0,8–0,9 мс.
- **После правки.** ПК: `SelectIndex` 1–1,5 мс, до `SwapBuffers` 4,5–7 мс, `tabs` max 12,7 мс. Эмулятор: `SelectIndex` 2,5–6 мс, до `SwapBuffers` 20–85 мс, `tabs` max 266,7 → 100 мс.
- **Остаток на эмуляторе** — это сама отрисовка кадра с сеткой в программном GL: в сценарии `grid` p50 50 мс и p95 83 мс. Поэтому кадр смены вкладки на эмуляторе не бывает короче 50 мс. Критерий проверяется на телефоне (отчёт пользователя) и ПК.

### После отчёта с телефона (2026-11-03)

- **`dy` на Android был неверен.** Время показа EGL приходит с задержкой в 2–3 кадра и иногда сразу для двух кадров, а смещение читалось в наблюдателе — в момент отчёта. Два кадра одного отчёта получали одно смещение (сдвиг 0 отбрасывался), следующий — двойной. Отсюда `dy` 0,3 даже у автопрокрутки, ровной по времени кадра (на ПК, где отчёт идёт сразу, 0,06). Правка: `Frame.Sample` — драйвер вызывает функцию `SetSampler` сразу после рисования кадра.
- **`dy` ручного замера не годился для решения D6.** Коэффициент вариации сдвига по всей сессии мерит разгон и торможение пальца (6–9), а не неровность от кадра к кадру. Новое определение — отклонение скорости за vsync от средней двух соседних (D3); плавный разгон даёт около 0.
- **`strip` на 120 Гц.** Куски страницы ленты были до 2048 px в высоту: на телефоне это 1440×2048 (12 МБ), загрузка такого куска в GPU за один кадр не укладывается в 8,3 мс (на 60 Гц — укладывается: `miss` 0%). Куски теперь 512 px (`stripSliceHeight`, на всех платформах): 1440×512 ≈ 3 МБ за кадр. Буфер страницы общий, памяти не добавляется; объектов изображения в 4 раза больше.
- **Решение D6 (касания)** — по ручному замеру следующей сборки с новым `dy`.
- **ПК после правок (21:48–21:58)** — сравнение кусков 512 и 2048 подряд, в одних условиях. ПК в это время был загружен сильнее, чем в 20:30 (запущен Steam): `grid` и `details`, которых правка не касается, тоже хуже прежнего, поэтому сравнивать надо прогоны между собой, а не с таблицей выше.

  | сценарий | 2048: 1v / miss | 512: 1v / miss | dy (512, новая формула) |
  |---|---|---|---|
  | grid | 98,1 / 2,0% | 99,1 / 0,9% | 0,044 |
  | strip | 89,9 / 9,1% | 92,5 / 7,0% | 0,065 |
  | paged | 86,8 / 11,8% | 91,1 / 8,1% | — |
  | details | 96,8 / 3,1% | 94,4 / 5,3% | 0,103 |

  Куски 512 в ленте лучше 2048. Критерий на ПК в 20:30 был выполнен; в загруженном состоянии `strip` его не держит при любой высоте куска.

- **Ручной замер после исправления (23:02):** `1v` 98,9%, `miss` 1,7%, `dy` 0,70; пользователь: «сейчас всё хорошо». `dy` ручного замера сейчас не отделяет перетаскивание от инерции Fyne: её шаги идут в горутине по 16 мс и не прекращаются от нового касания, так что при серии бросков хвост прошлого добавляет сдвиги к новому перетаскиванию; после пересчёта касаний последний сдвиг — за кадр, а не за точку сенсора, бросок длиннее и наложений больше.
