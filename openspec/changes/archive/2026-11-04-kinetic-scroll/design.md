## Context

Как сейчас работает отрыв пальца на телефоне (копия Fyne 2.8 в `third_party/fyne`):

- **`canvas.tapUp`** (`internal/driver/mobile/canvas.go`). Если шло перетаскивание, вызывает колбэк перетаскивания с последним сдвигом (`lastTapDelta`) для перетаскиваемого виджета и внешней прокрутки другого направления (`draggingOuter`), после чего завершает перетаскивание.
- **Колбэк в `tapUpCanvas`** (`internal/driver/mobile/driver.go`). Если сдвиг не больше 2 px, сразу вызывается `DragEnd`. Иначе горутина умножает сдвиг на 0,92, вызывает `Dragged` через `DoFromGoroutine` и спит 16 мс. Так повторяется, пока сдвиг не станет меньше 2 px, затем `DragEnd`.
- **Перетаскиваемые виджеты.** Это любые `fyne.Draggable`: прокрутка `widget.Scroll` (на мобильных `Dragged` сдвигает `Offset`), постраничный режим читалки `pagedView` (копит сдвиг и листает в `DragEnd`), разделители, ползунки.
- **После `frame-pacing`.** Движения касаний применяются по одному на кадр (`touchResampler`), анимации Fyne идут от времени кадра (`pacing.FrameTime`). На Windows `Scroll.Dragged` только для полос прокрутки.

Прокрутки приложения — `widget.Scroll`:
- `container.NewVScroll`: страница произведения, лента, настройки, поиск, ошибки;
- `widget.GridWrap`: сетка библиотеки и результатов поиска.

## Goals / Non-Goals

**Goals:**
- инерция с физикой Android: скорость по точкам пальца, путь и торможение по spline `OverScroller`;
- шаги инерции по кадрам;
- остановка касанием без нажатия;
- остановка на краю;
- накопление скорости при повторном броске;
- без инерции у всех перетаскиваемых виджетов, кроме прокруток;
- замер: сценарии броска и `dy` отдельно для пальца и инерции.

**Non-Goals:** отскок и подсветка края; горизонтальная инерция; инерция на ПК от мыши; настройка силы.

## Decisions

### D1. Пакет `internal/fling` в копии Fyne

Чистая физика (без виджетов) и запуск броска.

```go
// Spline — бросок с начальной скоростью v0 (dp/с) по формуле Android.
type Spline struct { V0, Distance float64; Duration time.Duration }
func NewSpline(v0 float64) Spline
func (s Spline) Position(t time.Duration) float64 // путь к моменту t, 0…Distance
func (s Spline) Velocity(t time.Duration) float64 // скорость к моменту t

// Start бросает target со скоростью v (dp/с по осям); onEnd — после остановки.
func Start(target fyne.Draggable, v fyne.Delta, onEnd func())
func Stop() bool    // остановить текущий бросок; true — он шёл
func Active() bool
```

**Физика** — порт `SplineOverScroller` из AOSP:
- `INFLEXION = 0,35`;
- `DECELERATION_RATE = ln 0,78 / ln 0,9`;
- трение `0,015` (`ViewConfiguration.getScrollFriction`);
- `physicalCoeff = 9,80665 × 39,37 × 160 × 0,84` — 160 «точек на дюйм» для dp, единиц Fyne;
- путь и длительность по `getSplineFlingDistance` и `getSplineFlingDuration`;
- форма торможения — таблица `SPLINE_POSITION` на 100 отрезков (P1 = 0,175, P2 = 0,35), построенная при инициализации тем же способом, что в AOSP.

Оси считаются отдельно, как `OverScroller` с `mScrollerX` и `mScrollerY`.

**Анимация.** Бросок — `fyne.Animation` длиной `Duration` (наибольшей из осей), кривая линейная. Такт (прогресс → время t) вызывает `target.Dragged` со сдвигом `Position(t) − уже пройдено` по каждой оси. Анимации идут от времени кадра (`frame-pacing`), поэтому шаги по кадрам ровные на любой частоте и на обеих платформах. Новых горутин и таймеров нет.

**Край.** Если `target` — `*widget.Scroll` и после `Dragged` смещение по оси не изменилось, ось останавливается. Когда остановлены обе оси, анимация прекращается, вызываются `DragEnd` и `onEnd`.

**Повторный бросок (flywheel, как `OverScroller.fling`).** Если бросок идёт по тому же `target` и знак новой скорости по оси совпадает с текущей скоростью (`Velocity(t)`), скорости складываются. При разных знаках бросок по оси начинается с новой скорости.

**Пределы.** Скорость по модулю ограничивается 8000 dp/с (`MAXIMUM_FLING_VELOCITY`). Меньше 50 dp/с (`MINIMUM_FLING_VELOCITY`) бросок по оси не начинается.

Одновременно идёт один бросок. Новый `Start` на другой `target` останавливает прежний и вызывает его `DragEnd`. Всё работает только в UI-потоке: `Start` вызывается из цикла драйвера или из `fyne.Do`.

### D2. Скорость пальца

`velocityTracker` в мобильном драйвере (чистая логика с тестами):
- хранит сырые точки последовательности касания `(t, x, y)` в единицах Fyne — до пересчёта на время кадра, как `VelocityTracker` в Android;
- при отрыве скорость считается квадратичным методом наименьших квадратов (LSQ2, по умолчанию в Android) по точкам за последние 100 мс до последней точки;
- если последняя точка движения старше 40 мс к моменту отрыва (палец остановился и стоял), скорость 0;
- меньше трёх точек — линейная оценка по двум крайним.

Точки добавляются в `TypeBegin` и `TypeMove` (вместе с промежуточными точками Android).

### D3. Отрыв пальца: замена колбэка в `tapUpCanvas`

- **Прокрутка (`*widget.Scroll`).** Если перетаскивался `*widget.Scroll` и скорость по его оси не меньше 50 dp/с, то `fling.Start(scroll, v, nil)`, а `DragEnd` вызывает бросок по окончании. Внешняя прокрутка другого направления (`draggingOuter`) получает бросок со своей составляющей скорости. Иначе — `DragEnd` сразу.
- **Не прокрутка** (`pagedView`, разделители, ползунки) — `DragEnd` сразу, без инерции. Свайп в постраничном режиме листает в момент отрыва; увеличенная страница двигается только за пальцем.
- Горутина Fyne с `time.Sleep(16 мс)` удаляется.

### D4. Касание во время броска

- В `TypeBegin`, если `fling.Active()`, бросок останавливается (`fling.Stop()`), а последовательность помечается «поймала бросок».
- Если такая последовательность закончилась без перетаскивания, в `canvas.tapUp` колбэки нажатия, второго нажатия и двойного нажатия не вызываются. Касание только остановило прокрутку. `TouchUp` для `mobile.Touchable` вызывается как обычно, чтобы виджеты не остались «нажатыми».
- Если палец после остановки повёл — обычное перетаскивание (и, возможно, новый бросок).
- Долгое нажатие во время броска (второе нажатие Fyne по времени удержания) тоже подавляется: та же пометка.

Тап-зоны ленты читалки и карточки сетки — обычные `Tappable`, поэтому подавление в драйвере покрывает их без изменений в нашем коде.

### D5. Замер

- **Вид движения кадра.** `internal/pacing` получает поле `Frame.Motion`: `""`, `"touch"` (палец на экране) или `"fling"` (идёт бросок). Его пишет `TakeSample` по состоянию драйвера (`SetMotion` из мобильного драйвера и `internal/fling`).
- **Сводка.** К прежнему `dy` добавляются `dyt` и `dyf` — та же неровность, но только по тройкам кадров, у которых средний кадр с пальцем или с броском. Если таких троек нет — `-`.
- **Сценарии `fling-grid` и `fling-strip`.** От начала списка три броска вниз со скоростью 3000 dp/с, каждый ждёт остановки (не дольше 4 с), затем один бросок вверх. Бросок запускается `frameclock.Fling(target, v)` → `driver/pacing.Fling` → `internal/fling.Start`, на обеих платформах. Прокрутку сценарий получает от экрана: `screens.ScrollTarget` получает метод `Draggable() fyne.Draggable`.
- **Критерии.** В сценариях броска `dyf < 0,1`, `1v ≥ 95%`. В ручном замере на телефоне `dyt` должен заметно упасть против `dy` 0,63–0,70 до изменения; цель ≤ 0,15 (требование «Касания по кадрам»).

### D6. Платформы и теги

| | Android | Windows |
|---|---|---|
| Инерция от пальца | да | — (у мыши нет перетаскивания прокрутки) |
| `fling.Start` из сценариев | да | да |
| Остановка касанием | да | — |

`internal/fling` без платформенных тегов. Правки драйвера — в `internal/driver/mobile`: там и Android, и тесты (`go test` на ПК с `test` driver не трогает мобильный драйвер, тесты физики и `velocityTracker` — чистые функции).

## Risks / Trade-offs

- **[Ощущение отличается от системных приложений]** → берутся константы и формулы AOSP. Плотность для расчёта — 160 точек на дюйм на dp, как в Android. Проверка — ваш тест на телефоне.
- **[Бросок дольше прежнего, а кнопки и карточки во время него не нажимаются]** → так в Android. Касание останавливает бросок сразу.
- **[`GridWrap` перестраивает ячейки при прокрутке]** → бросок двигает тот же `Scroll`, что и палец. Бюджет обложек и предзагрузка (`perf-and-layers`) работают как при перетаскивании.
- **[Обновление Fyne]** → новые места помечены `// mangareader:`, в `PATCHES.md` отдельный раздел.

### D7. Пересчёт касаний: задержка по факту (по отчёту с телефона)

`dyt` 0,625 почти точно равен `dy` 0,633 до пересчёта касаний (`frame-pacing`): пересчёт не помогал вовсе. Причина: в `NativeActivity` касания идут через `ViewRootImpl`, который копит их и отдаёт пачкой раз за кадр по своему Choreographer (UI-поток). Наш кадровый колбэк — на том же vsync, но на потоке ввода, поэтому пачка этого кадра приходит то до нашего кадра, то после. Во втором случае свежая точка старше на период, положение на «vsync − 5 мс» угадывается экстраполяцией (не дальше `min(Δ/2, 8 мс)`, на сенсоре 240–480 Гц это 1–2 мс) — сдвиг скачет, как без пересчёта.

Решение: задержка пересчёта — наибольший возраст самой свежей точки к кадру за последние 32 кадра с движением, от 5 мс до 5 мс + 2 периода. Там, где точки приходят сразу, остаются 5 мс; где пачками — около периода + 5 мс (≈ 13 мс при 120 Гц), и положение всегда между настоящими точками. Заодно интерполяция идёт при любом промежутке между точками: порог 2 мс (`RESAMPLE_MIN_DELTA`) на сенсоре 480 Гц срабатывал часто и «прилеплял» положение к старшей точке.

Модель в `TestTouchResamplerBatchedDelivery` (сенсор 480 Гц, экран 120 Гц, пачка опаздывает в каждом 3-м и 7-м кадре): с постоянными 5 мс сдвиги 3,96 и 8,33 вперемешку, с подбором — 8,33 ± 0,01. Выбранная задержка — в сводке (`tlat`), на телефоне она подтвердит объяснение: ≈ 13 мс — пачки, 5 мс — нет.

**Ручной замер после D7 (13:26):** `dyt` 0,625 → 0,259, `dyf` 0,290, `tlat` 21,1 мс; пользователь: «по ощущениям всё работает нормально». Два остатка:

- **Задержка у потолка** (5 мс + 2 периода = 21,7 мс вместо ожидаемых ~13). Возраст свежей точки засчитывался, пока последняя точка пришла меньше 2 периодов назад, — и при остановке пальца тоже: точек нет, возраст растёт до потолка. Теперь опоздание кадра засчитывается задним числом, только если потом пришли точки, существовавшие уже к тому кадру, и без паузы (> 20 мс) перед ними. Тест `TestTouchResamplerPauseKeepsLatency` (сенсор 240 Гц, пауза 100 мс): без этого условия задержка уходит в 21,67 мс, с ним остаётся 5 мс; модель пачек по-прежнему даёт ровные сдвиги.
- **Рывок при отрыве** (`dyf` 0,135 → 0,290 и часть `dyt`): перед концом касания применялось накопленное движение — при задержке 21 мс это 21 мс движения за один кадр, а затем бросок. Теперь, если отрыв начнёт бросок (`willFling`), отставание не догоняется: бросок начинается с показанного положения, как в Android. Без броска (медленный отрыв, не прокрутка) накопленное движение применяется, как раньше.

**Сдача (2026-11-04):** пользователь: «по ощущениям всё работает нормально»; изменение архивировано без ручного замера после 7.2 — критерий `dyt ≤ 0,15` подтверждён только моделью (`TestTouchResamplerBatchedDelivery`, `TestTouchResamplerPauseKeepsLatency`). Проверить при следующем замере: `dyt`, `tlat` (≈ 13 мс при доставке пачками).
