## Context

- `user.db` (`internal/userdata`): записи произведений `works(uid, root, rel, fingerprint, orphaned_at)`, миграции по `PRAGMA user_version` (сейчас 2: `user_tags`, `meta`). Запись создаётся лениво (`Ensure`), переносится по отпечатку при сверке (`Reconcile`), данные ссылаются на `uid` с `ON DELETE CASCADE`. Из UI-потока база не вызывается.
- `internal/app.Services` связывает библиотеку и userdata (`userDataObserver`: ключ папки `root`, сверка после сканирования).
- Читалка (`internal/ui/reader`) открывается `Reader.Open(g)` с первой страницы; после `reader-navigation` есть `SetOnFinished(func(model.Gallery))`.
- Страница произведения (`internal/ui/details`) строит кнопку «Читать»; меню — `screens.GalleryActions` (синхронно, в UI-потоке).

Ограничение: меню и кнопки строятся в UI-потоке, поэтому состояние прогресса должно читаться из памяти.

## Goals / Non-Goals

**Goals:** позиция по имени страницы с запасным номером; «Продолжить»; «дочитано» с продолжением после дополнения архива; сброс; без обращений к базе из UI-потока и без задержек листания.

**Non-Goals:** индикаторы прогресса на карточках, фильтры, «Продолжить» в меню карточки, синхронизация.

## Decisions

### 1. Схема: миграция 3

```sql
CREATE TABLE progress(
  uid        INTEGER PRIMARY KEY REFERENCES works(uid) ON DELETE CASCADE,
  page       TEXT    NOT NULL,   -- имя файла страницы в архиве (model.Page.Name)
  page_index INTEGER NOT NULL,   -- 0-based номер на момент сохранения
  total      INTEGER NOT NULL,   -- число страниц на момент сохранения
  finished   INTEGER NOT NULL,   -- 0/1
  updated_at INTEGER NOT NULL)   -- UnixNano
```

Методы `Store`: `AllProgress(root) (map[rel]Progress, error)` (одним запросом с JOIN на `works`), `SetProgress(uid, Progress)` (UPSERT), `ClearProgress(uid)`. Одна строка на произведение — история не нужна.

Отклонено: хранить только номер — ломается при удалении страниц в середине (решение из обсуждения); хранить в `settings.json` — не переживает перемещение файла и не чистится вместе с записями-сиротами.

### 2. Служба прогресса в `internal/app` с кэшем в памяти

```
          UI-поток                                   фон
 ┌───────────────────────────┐   Save/Finish/Reset   ┌──────────────────────┐
 │ progress.Get(rel) → mem   │ ───────────────────▶  │ writer (одна горутина│
 │ (mutex, без базы)         │   (обновляет mem      │ по очереди): Ensure, │
 └───────────────────────────┘    сразу, ставит      │ SetProgress / Clear  │
           ▲                       в очередь)        └──────────────────────┘
           │ reload(root): после Reconcile и смены папки (фон) → onChanged (fyne.Do)
```

- `Progress` — `Services.Progress *ProgressService` (nil-безопасные методы: при `UserData == nil` `Get` возвращает «нет», запись — no-op).
- Кэш `map[rel]Progress` текущей папки загружается в фоне при запуске (после `attachUserData`) и перезагружается после каждой сверки (`userDataObserver.Scanned`: перенос записи меняет `rel`) и смены папки (`setKey`). После перезагрузки — колбэк `onChanged`, который UI вызывает через `fyne.Do` (обновить открытую страницу произведения).
- Запись — одна фоновая горутина с очередью: порядок операций по произведению сохраняется, поэтому «дочитано» не будет перезаписано отложенной позицией (требование «Отметка «дочитано»»). Ошибки записи — в журнал, без сообщения пользователю.

Отклонено: прогресс в `model.Gallery` через наложение библиотеки (как теги) — `Library.Refresh` на каждое сохранение перерисовывал бы сетку.

### 3. Восстановление позиции — чистая функция

`app.Resume(p Progress, pages []model.Page) (page int, ok bool, approx bool)` по правилам требования «Продолжение чтения»: поиск имени — линейный по `pages` (сотни элементов). Позиция 0 без «дочитано» → `ok = false`. Тестируется таблицей без UI.

### 4. Читалка: открытие на странице и уведомления

- `Reader.Open(g model.Gallery, page int)`; «Читать» передаёт 0. `approx` → тост «Архив изменился…» после открытия.
- `Reader.SetOnPage(func(g model.Gallery, page int))` — вызывается при смене страницы, только после первой смены в текущем открытии (флаг `moved`), и при закрытии, если `moved`. Лента сообщает верхнюю страницу (уже вычисляется для панели).
- Задержка сохранения (≤ 1 с) — в `Shell`: таймер на последнюю позицию, сбрасывается при каждой смене; при закрытии и при «дочитано» таймер сбрасывается немедленной постановкой в очередь. `onFinished` из `reader-navigation` → `Progress.Finish(g)` (имя последней страницы, `finished = 1`).
- Во время перемещения ползунка (`scrubbing`) смена страницы не сообщается — сообщается после отпускания.

### 5. UI

- `details`: `SetProgress(get func(model.Gallery) (page int, ok bool))` и метод `RefreshProgress()`; рядом с «Читать» — кнопка «Продолжить · стр. N» (`widget.Button`, обычная важность, «Читать» остаётся основной). Обновляется при открытии страницы, при закрытии читалки (Shell) и по `onChanged`.
- Меню: в `GalleryActions` поле `ResetProgress func(model.Gallery)` и предикат `HasProgress func(model.Gallery) bool`; пункт добавляется в `tail` перед разделителем, если предикат истинен. `Shell.resetProgress` → `Progress.Reset(g)`, toast, `Details.RefreshProgress()`.

### Потоки

База — только в фоне (writer, reload). Кэш — под mutex, читается из UI-потока. Колбэки из фона в UI — через `fyne.Do`. Читалка вызывает `onPage` в UI-потоке; таймер задержки сохранения в Shell возвращается через `fyne.Do` или ставит в очередь напрямую (очередь потокобезопасна).

### Платформы

Windows и Android одинаково, build tags не нужны. Ключ папки (`root`) уже различается по платформам внутри `userDataObserver`.

## Risks / Trade-offs

- [Кэш устарел между сканированием и перезагрузкой] → перезагрузка сразу после `Reconcile` в той же горутине; окно — доли секунды, худший случай — нет кнопки «Продолжить» до следующего открытия страницы.
- [Закрытие приложения до записи из очереди] → при выходе (`Shell` закрытие окна / пауза Android) — дождаться очереди с таймаутом 1 с; потеря последней позиции не критична.
- [Переименование всех файлов при перепаковке] → запасной номер и подсказка о неточности.
- [Порядок с `reader-navigation`] → это изменение применяется после него (нужен `SetOnFinished`).

## Migration Plan

Миграция 3 добавляет таблицу, существующие данные не трогает. Откат: старая версия видит `user_version = 3` и работает без пользовательских данных (существующее требование «Миграции схемы»), файл не изменяется.
