## Context

Как Fyne 2.8.0 создаёт текстуру для `canvas.Image` с `Image != nil` (`internal/painter/image.go`, `internal/painter/gl/texture.go`):

```
paintImage: размер картинки ≠ размер виджета в px?
  └─ ScaleMode == Smooth → draw.CatmullRom.Scale в новый NRGBA   ← UI-поток
imgToTexture: не *image.RGBA?
  └─ draw.Draw в новый RGBA                                     ← UI-поток
TexImage2D
```

Для `ImageScaleFastest` и `ImageScalePixels` программного масштабирования нет, картинка уходит как есть. На GPU у `Smooth` и `Fastest` один фильтр (`GL_LINEAR`, `textureFilterToGL`). `*image.RGBA` загружается без копии.

Все наши изображения используют `Smooth`, и размеры почти всегда не совпадают:
- **Страницы.** `pages.Normalize` округляет размер запроса вверх до 64 px. Лента на экране 1440 px запрашивает 1472 px.
- **Миниатюры.** `DefaultMaxSide = 320`, а карточка на телефоне около 450×640 px. Fyne ограничивает цель размером исходника, поэтому CatmullRom пересчитывает картинку в тот же размер, то есть просто копирует.
- **Формат.** `scaleToBox` и `Downscale` возвращают NRGBA, а без уменьшения исходник остаётся `YCbCr` (JPEG). `Slice` копирует каждый кусок в новый NRGBA.

Мобильный драйвер (`internal/driver/mobile/driver.go`) обрабатывает всё в одной горутине: касания, `fyne.Do`, отрисовку. Кадры запускает `time.NewTicker(time.Second / 60)`, без привязки к vsync. Поэтому любая работа по созданию текстуры задерживает и кадр, и обработку пальца.

Лента (`stripView.updateVisible`) вызывается из `scroll.OnScrolled` на каждое событие прокрутки и каждый раз делает `loader.NewGeneration()`, `request` для всех страниц окна и `content.Refresh()`. Последнее означает `contentRenderer.Layout` (перемещение всех страниц) и `Canvas().Refresh(content)`: `FreeDirtyTextures` обходит всё поддерево и освобождает текстуры всех объектов, кроме `canvas.Image` (надписи, прямоугольники), и они рисуются заново. Во время прокрутки положения страниц внутри `content` не меняются, их сдвигает `container.Scroll`.

`thumbs.Cache.Load` на каждый запрос запускает горутину, которая ждёт семафора (`min(4, NumCPU)`). Отмены нет, очередь по сути FIFO. Кэш на 300 записей.

## Goals / Non-Goals

**Goals:** сначала исходный замер кадров, затем ни одного программного масштабирования или конвертации изображений в UI-потоке; прокрутка ленты без перестройки раскладки внутри окна; миниатюры по размеру карточки с отменой и LIFO; ровный такт кадров на Android 120 Гц; инструмент, который покажет, нужен ли форк драйвера.

**Non-Goals:** форк драйвера Fyne, миниатюры на диске, память браузера, лимиты кэша читалки.

## Decisions

### D1. Всё в `*image.RGBA` и `ImageScaleFastest`

- Функция `pages.toRGBA(img)`: если это уже `*image.RGBA` с `Rect.Min == (0,0)`, возвращает как есть, иначе делает `draw.Draw(dst, …, draw.Src)` в новый RGBA. Вызывается в фоне, у воркера загрузчика.
- `scaleToBox` рисует в `image.NewRGBA` вместо NRGBA. Если уменьшать не нужно, возвращает `toRGBA(src)`.
- `thumbs.Downscale` → RGBA; маленькие изображения тоже проходят через `toRGBA`. Функция экспортируется из `pages`, чтобы не дублировать её: `thumbs` уже зависит от `golang.org/x/image/draw`, импорт `pages` из `thumbs` цикла не даёт. Альтернатива — положить её в небольшой общий пакет `internal/imgutil`. Отклонено: лишний пакет ради одной функции.
- `ScaleMode = canvas.ImageScaleFastest` в `card.go`, `paged.go`, `strip.go` и `details.go`.

Для непрозрачных страниц NRGBA и RGBA побайтно совпадают. Для PNG с прозрачностью `draw.Src` в RGBA даёт премультиплицированные значения, а именно их и ждёт Fyne (`imgToTexture` копирует в RGBA через `draw.Over` поверх прозрачного, это тоже премультиплицированный RGBA). Внешний вид не меняется.

Альтернатива — запрашивать страницы точно по размеру виджета, без округления до 64. Отклонено: округление нужно, чтобы мелкий ресайз не порождал новые декодирования. С `Fastest` разницу до 63 px бесплатно сглаживает GPU.

### D2. `Slice` без копирования

У RGBA полной ширины `SubImage(Rect(0, y, w, y+h))` даёт `*image.RGBA` с `Pix`, который начинается в начале нужной строки, и `Stride == w*4`. `imgToTexture` загружает `Rect.Size()` пикселей с начала `Pix`, построчно без пропусков. Это корректно, потому что кусок занимает всю ширину. `Slice` проверяет, что вход `*image.RGBA` с `Stride == Dx*4`, иначе сначала вызывает `toRGBA`. Все куски держат ссылку на один буфер, и кэш загрузчика считает его один раз: `put` суммирует `Bounds()` кусков, сумма совпадает с полным размером.

Риск: `Rect.Min` куска не `(0,0)`, а Fyne берёт только `Rect.Size()` и `Pix`. Это проверено по коду Fyne 2.8 и закрепляется тестом, который сравнивает `Pix[0:4]` куска с пикселем исходника в строке `y`.

### D3. Миниатюры: очередь, отмена, лимит, размер

```
Load(g, cb) → cancel()
  ├─ в кэше           → go cb(img, err); cancel = no-op
  ├─ уже в работе     → добавить waiter; cancel убирает waiter
  └─ новый            → job в стек (LIFO), воркеры (фиксированное число) берут с вершины
воркер: pop → живых waiters нет? → выбросить без декодирования
        иначе decode → put (лимит байт) → вызвать живых waiters
```

- **API.** `Load` возвращает `func()` для отмены. `galleryCard` хранит `cancel` и вызывает его, когда `updateCard` переиспользует карточку, до нового `Load`.
- **Воркеры.** Постоянные горутины с `sync.Cond`, как в `pages.Loader`: без горутины на каждый запрос. Число воркеров и лимит кэша задают платформенные файлы `internal/app/app_android.go` (2 воркера, 48 МБ) и `app_desktop.go` (`min(4, NumCPU)`, 64 МБ) через параметры `newServices`.
- **Кэш.** Лимит в байтах (`w*h*4`): 48 МБ на мобильном, 64 МБ на ПК. `New(open, limitBytes, workers)`. Прежний `DefaultCapacity` удаляется.
- **Размер.** `SetBox(w, h)`: область обложки карточки в физических пикселях, каждая сторона не больше 512. Миниатюра вписывается в эту область (`Downscale(src, w, h)` через `pages.Fit`), поэтому и горизонтальная обложка не шире карточки. При изменении области кэш очищается, потому что старые миниатюры другого размера; результат декодирования, начатого до смены, не кэшируется. `galleryGrid` вызывает `SetBox(ceil(coverSize × canvas.Scale()))` в каждом `updateCard` (без изменения — no-op). `Load` вызывается только после того, как известен масштаб (`fyne.CurrentApp().Driver().CanvasForObject(grid)` не nil), чтобы не декодировать обложку в размере по умолчанию.
- **Отмена в карточке.** `galleryCard.cancel` хранит отмену текущей загрузки. Если `updateCard` переиспользует карточку для другой галереи, прежний запрос отменяется до нового `Load`. Если карточку обновляют для той же галереи, пока обложка грузится, второй запрос не ставится.
- **Ошибки в кэше.** Закэшированная ошибка «весит» 64 байта, чтобы кэш ошибок тоже был ограничен.
- **Потоки.** Колбэк по-прежнему вызывается из фоновой горутины. `galleryGrid` передаёт результат через `g.do` (`fyne.Do`) и проверяет `thumbKey`, как сейчас. `cancel` вызывается из UI-потока, внутри он берёт `c.mu`.

### D4. Частота экрана: `internal/display` + Kotlin

- **Пакет `internal/display`.** `SetMax60(on bool) error`. `display_android.go` и `display_android.c` вызывают через JNI статический `io.github.mangareader.app.DisplayRate.apply(Activity, boolean)` загрузчиком классов приложения, по образцу `mbClear` в `internal/mobilebrowser/jni_android.c`. `display_other.go` — заглушка, `Supported = false`.
- **Kotlin `DisplayRate.apply`.** Выполняется в `activity.runOnUiThread`. Если `on`, среди `display.supportedModes` выбирается режим с тем же `physicalWidth`/`physicalHeight` и частотой, ближайшей к 60, и ставится `window.attributes.preferredDisplayModeId = mode.modeId`. Если такого режима нет, `preferredRefreshRate = 60f`. Если `off`, оба значения обнуляются (`0`). Вызов `window.attributes = lp`. Исключения ловятся и пишутся в `Log.w`.
- **Почему `preferredDisplayModeId`.** На Samsung с адаптивной частотой система может игнорировать один только `preferredRefreshRate`. `Surface.setFrameRate` / `ANativeWindow_setFrameRate` требует доступа к окну NativeActivity изнутри Fyne. Отклонено.
- **Когда применять.** При старте, из `ui.Shell` после создания окна, в `fyne.Do` / `RunNative`. При изменении флажка в настройках. На `lifecycle.OnEnteredForeground`, потому что после возврата из `BrowserActivity` окно наше, но атрибуты сохраняются в объекте окна Activity, и повтор безвреден. `BrowserActivity` — другое окно, его не трогаем.
- **Настройка.** Ключ `display.max60` (`"1"`/`"0"`, по умолчанию `"1"`) в `internal/app` — `app.KeyDisplayMax60`, `app.DisplayMax60(settings) bool`.

### D5. Замер кадров — тег `frameprobe` (делается первым)

Инструмент замера реализуется **до** оптимизаций. Иначе не будет исходных цифр и нельзя понять, что дала каждая мера. Порядок работы и замеров:

```
замер A  исходный код + frameprobe               ← база
D1–D3, D7 (RGBA, Fastest, лента, миниатюры)
замер B  то же, 60 Гц ещё нет                   ← эффект снятия нагрузки
D4 (60 Гц)
замер C  «Ограничить 60 Гц» вкл/выкл            ← эффект частоты
```

Сценарии каждого замера одинаковые: 30 с прокрутки сетки библиотеки, 30 с прокрутки ленты на произведении в 34 страницы, 30 с листания в постраничном режиме.

- `internal/ui/frameprobe_on.go` (`//go:build frameprobe`) и `frameprobe_off.go` (пустой `startFrameProbe()`).
- Замер: бесконечная `fyne.Animation` (`RepeatCount = fyne.AnimationRepeatForever`, `Tick` пишет `time.Now()` в кольцевой буфер). Мобильный драйвер зовёт `TickAnimations` в каждом `handlePaint`, то есть на каждом такте тикера. Интервал между тиками равен фактическому шагу цикла UI. Если UI-поток занят созданием текстур или колбэками, интервал растёт.
- Раз в 5 секунд в журнал пишется `frameprobe: n=… p50=…ms p95=…ms max=…ms >25ms=…`. На Android журнал Go попадает в logcat.
- Анимация сама по себе ничего не перерисовывает, `Tick` пустой по смыслу, поэтому лишней нагрузки на GPU нет.
- **Как читать.** Если p95 и max большие (≫ 16,7 мс), причина в нагрузке на UI-поток, и искать надо дальше в нашем коде. Если p95 около 16,7 мс, max без выбросов, а рывки всё равно видны, причина в рассинхроне фазы тикера с vsync. Запрос 60 Гц его не убирает, остаётся форк драйвера с отрисовкой по `Choreographer` (шаг 4, отдельное изменение).
- **Ограничение.** Замер показывает шаг цикла UI, но не момент показа кадра на экране. Рассинхрон с vsync он косвенно выдаёт только как «ровные интервалы при видимых рывках». Для подтверждения есть `adb shell dumpsys SurfaceFlinger --latency` или «Профилирование GPU» в параметрах разработчика.
- **Сборка.** `tools/android-build -tags frameprobe` добавляет теги к `migrated_fynedo`. Makefile получает `EXTRA_TAGS ?=` (имя `TAGS` уже занято внутренней константой `migrated_fynedo`) и передаёт их в `run`, `build-windows` и `build-android`.

### D7. Лента: работа только при смене окна

`updateVisible` вычисляет `from, to` (окно размещения), `onScreenFrom, onScreenTo` (видимые страницы) и `top` и сравнивает их с прошлыми значениями в `stripView` (`lastFrom`, `lastTo`, `lastScreenFrom`, `lastScreenTo`). Если всё совпадает, функция сразу выходит: без `NewGeneration`, `request` и `content.Refresh()`. Если изменилось:
- **окно `[from, to)`:** освобождаются вышедшие, создаются вошедшие, выполняются `NewGeneration`, `request` для окна и `content.Refresh()`;
- **только видимые (приоритеты):** `NewGeneration` и `request` с новыми приоритетами, без `Refresh`;
- **только `top`:** `pageChanged`.

Принудительный пересчёт (`releaseAll`, который вызывают `layout`, `show` и `reset`, и `setHeight`) сбрасывает запомненные значения (`lastFrom = -1`); `goTo` сброса не требует — новое смещение само даёт другое окно, чтобы следующий `updateVisible` отработал полностью. `stripRenderer.Layout` вызывает `updateVisible` при каждом ресайзе, и там это безопасно: при неизменном окне это no-op.

`contentRenderer.Refresh` сейчас вызывает и `Layout`, и `Canvas().Refresh(r.c)`. После D7 он вызывается только при смене окна или высот, и `Canvas().Refresh` остаётся нужен, чтобы новые `box` попали в дерево объектов.

Альтернатива — оставить обновление на каждое событие, но убрать `Canvas().Refresh`. Отклонено: `Layout` всех страниц окна и `NewGeneration` (сортировка очереди загрузчика под мьютексом) на каждое событие касания тоже лишние.

### D6. Потоки (сводка)

Декодирование, масштабирование, конвертация и нарезка выполняются в воркерах `pages.Loader` и `thumbs.Cache`. Результаты приходят в UI через `fyne.Do` (`r.do`, `g.do`, `d.do`), как сейчас. `cancel()` миниатюр, `SetBox` и `display.SetMax60` вызываются из UI-потока. JNI идёт через `driver.RunNative`, Kotlin сам переходит в UI-поток Android.

## Risks / Trade-offs

- [Качество: GPU-билинейное сжатие на 1–4% вместо CatmullRom] → разница незаметна, а фильтр на GPU и так `GL_LINEAR`. Проверить на экране на тексте мелким шрифтом.
- [Миниатюра по размеру карточки на экране с большой плотностью больше прежней: 358×512 против 226×320, примерно 730 КБ против 290 КБ] → кэш ограничен в байтах (48 МБ ≈ 65 обложек), а в сетке видно 8–15 карточек. Вытеснение при длинной прокрутке — ожидаемое.
- [Система игнорирует запрос 60 Гц] → проверить на S25 Ultra через `adb shell dumpsys display | grep -i "mActiveModeId\|refresh"`. Если игнорирует, то это известное ограничение, а решение — форк драйвера (Non-goal).
- [60 Гц на 120-Гц телефоне кажется «хуже» тем, кто привык к 120] → флажок в настройках.
- [`SubImage`-куски удерживают весь буфер страницы, пока жив хоть один кусок] → куски одной страницы всегда показываются и освобождаются вместе (`stripItem`), поведение памяти то же.
- [Лишнее декодирование обложек при смене `SetBox`] → только при изменении масштаба экрана, то есть почти никогда.

## Migration Plan

Настройка `display.max60` по умолчанию включена. Кэш миниатюр живёт только в памяти, переносить нечего. Откат обычный, через revert.

## Open Questions

- Нужна ли форк-версия драйвера: решается по замерам A/B/C, отдельным change. Итоги замеров записываются сюда.

### Замер A (база, 26.09.2026)

Устройство: Galaxy S25 Ultra, экран 1440×3120, 120 Гц (режим `id=1`; режим 60 Гц с тем же разрешением есть, `id=3`). Сборка: код до оптимизаций + `EXTRA_TAGS=frameprobe`. Данные: 60 архивов по 3 страницы и один на 34 страницы (1280×1800 JPEG, 15 МБ). Строки `frameprobe` — окна по 5 с.

| Сценарий | p50 | p95 | max | кадров > 25 мс за 5 с | кадров за 5 с (из 300) |
|---|---|---|---|---|---|
| Простой | 16,4 | 17,4 | 17,7–23 | 0 | 300 |
| Сетка библиотеки, 30 с свайпов (холодный кэш) | 16,4 | 17,4 | 17,5–20,5 | 0 | 300 |
| Лента, 30 с свайпов (стр. 1→17) | 16,4 | 17,4 | **252–283** | 2–4 | 254–279 |
| Постраничный, касание раз в 1,2 с (стр. 17→32) | 16,4 | 17,4 | **181–249** | 2–4 | 264–283 |

Выводы:
- Вне остановок цикл UI идёт ровно на 60 Гц (p95 17,4 мс).
- **Каждое перелистывание — одна остановка на ~180–250 мс** (15 перелистываний → 16 остановок), **каждая новая страница в ленте — ~250–280 мс**. Размер совпадает с оценкой: CatmullRom по ~1440×2030 и копия в RGBA в UI-потоке (D1).
- Сетка библиотеки на этих данных остановок не даёт: миниатюра 226×320 обходится в единицы мс. Если рывки в сетке всё равно видны, это уже подача кадров на экран (рассинхрон тикера с vsync), а не нагрузка.
- Время показа кадров на экране получить не удалось: `dumpsys SurfaceFlinger --latency` для слоя пуст, `--timestats` без root не собирает (`totalFrames = 0`). Для этого нужен трейс Perfetto (FrameTimeline).
- При касаниях чаще ~0,5 с постраничный режим воспринимает их как двойные (увеличение ×2), поэтому листание в замерах идёт раз в 1,2 с.

### Замер B (после D1–D3, D7; без 60 Гц; 26.09.2026)

Те же устройство, данные и сценарии; экран 120 Гц.

| Сценарий | p50 | p95 | max | кадров > 25 мс за 5 с | кадров за 5 с |
|---|---|---|---|---|---|
| Сетка библиотеки, 30 с (холодный кэш) | 16,4 | 17,4 | 17,6–19,0 | 0 | 300–301 |
| Лента, 30 с (стр. 1→18) | 16,5–16,7 | 17,3–17,5 | 18,5–26,4 | 0–1 | 300–301 |
| Постраничный, раз в 1,2 с (стр. 1→16) | 16,4–16,7 | 16,8–17,6 | 19,2–28,1 | 0–1 | 300–301 |

Выводы:
- Остановки на 180–280 мс исчезли полностью: за 30 с ленты — один кадр 26 мс вместо 18 остановок; за 15 перелистываний — один кадр 28 мс вместо 16 остановок.
- Цикл UI теперь не теряет кадров (300 из 300 за 5 с) во всех сценариях.
- Миниатюры по размеру карточки заметно чётче прежних 320 px, пустых мест в ленте при быстрой прокрутке нет.
- Нагрузка на UI-поток больше не причина рывков. Если рывки ещё видны, остаётся подача кадров: 60-герцовый тикер на экране 120 Гц (проверяется замером C).

### Замер C (60 Гц; 26.09.2026)

- Запрос применяется: `DisplayRate` выбирает режим `id=3` (1440×3120, 60 Гц), `dumpsys SurfaceFlinger` показывает `activeMode … vsyncRate=60.00 Hz`, `peak-refresh-rate: 60.00 Hz`. Флажок в настройках переключает сразу: выкл → `120.00 Hz`, вкл → `60.00 Hz`. В `BrowserActivity` экран остаётся 120 Гц, после возврата в приложение — снова 60 Гц.
- Цикл UI с 60 Гц — как в замере B: сетка p50 16,4–16,6, p95 17,3–17,6, max ≤ 19,3, 0 кадров > 25 мс; лента p50 16,5–16,7, p95 17,2–17,5, max ≤ 23,3, 0 кадров > 25 мс. Так и ожидалось: 60 Гц меняет не работу цикла, а согласованность такта с экраном.
- Показ кадров на экране этим замером не измеряется (см. «Ограничение» в D5). Решение о форке драйвера (шаг 4) — по визуальной оценке на устройстве: если с включённым «Ограничить 60 Гц» прокрутка ровная, форк не нужен.

### Итог (26.09.2026)

Визуальная проверка на S25 Ultra: прокрутка ленты, листание и сетка ровные; качество страниц, обложек и обложки на странице произведения без потерь. **Форк драйвера Fyne (шаг 4) не нужен.** Вопрос закрыт; вернуться к нему, если рывки появятся на других устройствах — начать с замера `EXTRA_TAGS=frameprobe`.
