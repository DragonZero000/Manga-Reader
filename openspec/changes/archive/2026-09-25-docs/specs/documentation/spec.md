## ADDED Requirements

### Requirement: Документация на двух языках
Документация SHALL существовать на английском и русском с одинаковым составом:
- в корне — пары `README.md`/`README.ru.md` и `CONTRIBUTING.md`/`CONTRIBUTING.ru.md` (английский файл без суффикса, русский с суффиксом `.ru`);
- в `docs/` — папки `docs/en/` и `docs/ru/` с одинаковым набором имён файлов.

Каждый документ MUST начинаться с переключателя языка — строки со ссылкой на пару на другом языке. Изображения MUST храниться один раз в `docs/images/` и использоваться обоими языками. `THIRD_PARTY_NOTICES.md` и `LICENSE` существуют в одном экземпляре на английском.

#### Scenario: Переключение языка
- **WHEN** посетитель открывает `README.md` на GitHub и нажимает «Русский» в первой строке
- **THEN** открывается `README.ru.md`, в первой строке которого есть ссылка обратно на `README.md`

#### Scenario: Парность docs
- **WHEN** в `docs/en/` есть `user-guide.md`, `building.md`, `architecture.md`
- **THEN** в `docs/ru/` есть файлы с теми же именами, и наоборот

### Requirement: Автоматическая проверка документации
`go test ./...` SHALL проверять:
- у каждого `*.md` в `docs/en/` есть файл с тем же именем в `docs/ru/`, и наоборот;
- у `README.md` и `CONTRIBUTING.md` есть пары `.ru.md`;
- каждый двуязычный документ содержит в первых строках ссылку на свою пару;
- каждая относительная ссылка в этих документах (Markdown-ссылки и изображения, без `http(s):`, `mailto:` и якорей внутри страницы) указывает на существующий файл или папку.

Сообщение об ошибке MUST называть файл и проблему. Проверка MUST работать без сети.

#### Scenario: Забытый перевод
- **WHEN** добавлен `docs/en/faq.md`, а `docs/ru/faq.md` нет
- **THEN** `go test ./...` падает с сообщением, что для `docs/en/faq.md` нет `docs/ru/faq.md`

#### Scenario: Битая ссылка
- **WHEN** в `docs/ru/building.md` есть ссылка `[архитектура](architektura.md)`, а такого файла нет
- **THEN** `go test ./...` падает с сообщением, где именно ссылка и на что она указывает

#### Scenario: Внешние ссылки
- **WHEN** документ ссылается на `https://github.com/DragonZero000/Manga-Reader/releases`
- **THEN** проверка эту ссылку пропускает и в сеть не обращается

### Requirement: README как витрина проекта
`README.md` и `README.ru.md` SHALL содержать:
- что это за приложение, одним абзацем;
- список возможностей;
- скриншоты из `docs/images/`, если они есть;
- явную пометку, что интерфейс пока только на русском;
- раздел «Скачать» (ссылка на Releases, назначение каждого файла релиза, проверка контрольных сумм);
- установку на Windows и Android (включая обновление APK поверх);
- системные требования;
- краткий раздел для разработчиков со ссылками на `building.md`, `architecture.md` и `CONTRIBUTING`;
- лицензию и ссылку на `THIRD_PARTY_NOTICES.md`.

Подробности (формат архива, браузер, секреты) MUST находиться в `docs/`, а не в README.

#### Scenario: Новый посетитель
- **WHEN** человек, не знающий русского, открывает страницу репозитория
- **THEN** из `README.md` он понимает, что это читалка манги для Windows и Android со встроенным браузером, что интерфейс пока только на русском и какой файл скачать для своей платформы

#### Scenario: Системные требования
- **WHEN** пользователь ищет, подойдёт ли приложение его устройству
- **THEN** в README указаны Windows 10/11 x64 и Android 11+ arm64, а также что Linux пока не поддерживается

### Requirement: Руководство пользователя
`docs/<язык>/user-guide.md` SHALL описывать фактическое поведение приложения: папку библиотеки на ПК (портативный режим) и на Android (выбор папки), формат архива и поля `meta.json`, экран «Библиотека», страницу произведения, читалку (режимы, управление, клавиши), поиск и его синтаксис, встроенный браузер на Windows и Android, вкладку «Ошибки» и настройки. Названия элементов интерфейса MUST приводиться так, как они написаны в приложении (по-русски); в английской версии — с переводом в скобках при первом упоминании.

#### Scenario: Синтаксис поиска
- **WHEN** пользователь хочет найти произведения с тегом, но без другого тега
- **THEN** в руководстве есть раздел о синтаксисе поиска с примером исключения тега

#### Scenario: Соответствие приложению
- **WHEN** в руководстве описана кнопка или раздел настроек
- **THEN** такой элемент есть в текущей версии приложения с тем же названием

### Requirement: Документация для разработчиков
`docs/<язык>/building.md` SHALL описывать требования для сборки, команды `make`, сборку Android, версию в `FyneApp.toml`, выпуск релиза и пошаговую настройку ключа подписи и секретов GitHub. `docs/<язык>/architecture.md` SHALL описывать пакеты и их границы, платформенные build-теги, правило обновления UI через `fyne.Do`, устройство встроенного браузера на обеих платформах, инструменты в `tools/`, CI и назначение `openspec/`. `CONTRIBUTING` SHALL описывать порядок предложения изменений, обязательные проверки, процесс OpenSpec, правило двух языков документации, язык строк интерфейса и обновление `THIRD_PARTY_NOTICES.md`.

#### Scenario: Сборка с нуля
- **WHEN** разработчик на Windows с установленными Go, gcc и Android Studio следует `building.md`
- **THEN** он получает `dist/mangareader.exe` и `dist/mangareader.apk`, не обращаясь к другим источникам

#### Scenario: Новый пакет
- **WHEN** участник добавляет пакет в `internal/`
- **THEN** из `CONTRIBUTING` и `architecture.md` он знает, что пакет нужно добавить в `internal/archtest` и в описание архитектуры на обоих языках
