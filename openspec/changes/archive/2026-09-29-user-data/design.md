## Context

- `library.db` (`internal/catalog`) — восстанавливаемый кэш. Он пересоздаётся при смене `schemaVersion`/`search.NormVersion`, при повреждении, а при смене папки очищается (`Reset`). Хранить там данные, которые нельзя восстановить из архивов, нельзя.
- Единственные пользовательские данные сейчас — ссылки скачанных файлов (Android): `links.json` плюс копия в каталоге. Они привязаны к `rel` и при пропаже файла удаляются (`PruneLinks`).
- Ключ произведения `model.Key{local, rel}` — это путь, а он меняется при переименовании и перемещении.
- Все сканирования (запуск, «Обновить», наблюдение за папкой, возврат на передний план) проходят через `library.Source.Scan`, удаление — через `Source.Delete`. Оба выполняются вне UI-потока.
- Поддерживаются только `.zip`, и в оглавлении zip у каждой записи всегда есть CRC32 и несжатый размер.
- Следующее изменение `custom-tags` будет хранить тэги в этой же базе.

## Goals / Non-Goals

**Goals:** постоянная база с миграциями; стабильный `uid` произведения; отпечаток содержимого; безопасная сверка с переносом и сроком хранения; настройка срока; API, на который лягут тэги, группы и прогресс.

**Non-Goals:** UI самих данных; перенос между разными папками библиотеки; экспорт и импорт; форматы кроме zip.

## Decisions

### D1. Отдельный файл `user.db` и пакет `internal/userdata`

Это отдельный файл, а не таблицы в `library.db`: у каталога жизненный цикл «удалить и пересоздать», и защищать отдельные таблицы от этого сложнее и рискованнее, чем держать два файла. Драйвер тот же, `github.com/mattn/go-sqlite3` (уже в go.mod), без FTS5, поэтому тег `sqlite_fts5` пакету не нужен. Параметры подключения: WAL, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`.

- Отклонено: таблицы в `library.db` с исключением из `Reset`/пересоздания — пересоздание удаляет файл целиком.
- Отклонено: JSON-файл, как `links.json` — будущие группы и прогресс потребуют запросов и связей, а весь JSON пришлось бы переписывать на каждое изменение.

Сервисный пакет без виджетов добавляется в `internal/archtest`.

### D2. Схема v1 и миграции

```sql
CREATE TABLE works(
  uid         INTEGER PRIMARY KEY,
  root        TEXT NOT NULL,     -- ключ папки библиотеки (D3)
  rel         TEXT NOT NULL,     -- путь относительно папки, со слешами '/'
  fingerprint TEXT NOT NULL,     -- D4
  orphaned_at INTEGER,           -- UnixNano; NULL — файл на месте
  UNIQUE(root, rel));
CREATE INDEX works_fp ON works(root, fingerprint);
```

Будущие таблицы ссылаются на `uid ... REFERENCES works(uid) ON DELETE CASCADE`, поэтому удаление сироты удаляет и её данные.

`migrations []func(*sql.Tx) error`; `PRAGMA user_version` = число применённых миграций. Недостающие применяются в одной транзакции вместе с установкой версии. Если версия больше `len(migrations)`, `Open` возвращает `ErrNewerSchema`, файл не трогается, приложение работает без пользовательских данных.

### D3. Ключ папки библиотеки

- ПК: константа `app:manga`. Папка библиотеки всегда `<папка приложения>/manga`, и при переносе портативной папки абсолютный путь меняется, а данные должны остаться. `library.db` при этом, как и раньше, пересканирует папку (это кэш).
- Android: tree-URI SAF (`library.tree`). Повторный выбор той же папки даёт тот же URI.

Ключ вычисляет `internal/app`; `userdata` принимает его строкой.

### D4. Отпечаток

В `library.ReadArchive` для каждой страницы берутся `zip.File.Name`, `CRC32`, `UncompressedSize64`. Строки `name\x00crc\x00size\n` сортируются побайтно по `name`, затем берётся SHA-256 в hex. Результат хранится в `model.Gallery.Fingerprint` (JSON `omitempty`) и попадает в кэш каталога вместе с галереей.

- Набор файлов тот же, что у `g.Pages` (картинки, без служебных), поэтому правка `meta.json` отпечаток не меняет.
- `catalog.schemaVersion` 2 → 3: старые записи без отпечатка отбрасываются, библиотека один раз пересканируется целиком.
- Отклонено: хеш всего файла — чтение всего архива, и меняется при правке meta.json. `ExternalID` — у разных сайтов номера пересекаются. Только размер плюс число страниц — много ложных совпадений.

### D5. Наблюдатель в `library.Source`

```go
// Observer получает события источника в горутине сканирования/удаления (не UI).
type Observer interface {
    Scanned(res ScanResult) // после успешного обхода, под scanMu, ДО публикации списка и индекса
    Deleted(rel string)     // после успешного Delete
}
func (s *Source) SetObserver(o Observer)
```

`Scanned` вызывается сразу после `scanner.Scan`, до замены `s.galleries` и `updateIndex`. Так данные, перенесённые по отпечатку, уже учтены, когда `custom-tags` накладывает их на галереи этого же скана. `library` не зависит от `userdata`. Адаптер в `internal/app` превращает `ScanResult` в `map[rel]fingerprint`:
- `Galleries` дают путь и отпечаток;
- `Errors` и `Busy` дают путь с пустым отпечатком (файл есть, но разобрать его нельзя).

Затем адаптер вызывает `Store.Reconcile(root, files, now, retention)`. Незавершённые загрузки в `ScanResult` не входят: для них записи ещё нет.

### D6. Сверка — одна транзакция

```
recs    := works WHERE root = ?
1. rec.rel ∈ files      → orphaned_at = NULL; fp ≠ "" и ≠ rec.fp → обновить fp
2. missing := recs, чей rel ∉ files (и уже сироты, и пропавшие в этом скане)
   fresh   := rel ∈ files без записи, fp ≠ ""
   для fp: |missing(fp)| = 1 и |fresh(fp)| = 1 → rel := новый, orphaned_at = NULL
3. len(files) > 0 → оставшимся missing с orphaned_at IS NULL: orphaned_at = now
4. retention > 0 → DELETE WHERE root = ? AND orphaned_at < now − retention
```

На шаге 2 кандидатами становятся и записи, пропавшие в этом же скане, поэтому переименование при работающем приложении переносится за одно сканирование. Шаг 4 выполняется и при пустой папке: он удаляет только сирот, помеченных раньше.

`Deleted(rel)` → `MarkOrphan(root, rel, now)`, если запись есть и ещё не сирота.

Записей немного (только произведения с данными), поэтому сверка выполняется в памяти одной транзакцией, без заметной задержки сканирования.

### D7. Открытие и восстановление

`userdata.Open(path) (*Store, Recovery, error)`:
- открыть и выполнить `PRAGMA quick_check`;
- если это не SQLite или проверка не прошла, закрыть и переименовать `user.db` (+`-wal`, `-shm`) в `user.db.broken-20260930-142501`, создать новую базу, вернуть `Recovery{Backup: путь}`;
- если переименование или создание не удались, вернуть ошибку: `Services.UserData = nil`, приложение работает без пользовательских данных.

`Services` получает `UserData *userdata.Store` и `UserDataBackup string`. Оболочка при запуске (`SetOnStarted`, UI-поток) показывает toast `userdata.recovered`, если путь не пустой. `Services.Close` закрывает базу.

### D8. Настройка срока

Ключ `userdata.retention` — число дней строкой; `"0"` означает «бессрочно»; по умолчанию `"30"`. Функции `app.Retention(s) time.Duration` (0 = бессрочно) и `app.SetRetentionDays(s, n)`. Недопустимое сохранённое значение трактуется как 30.

UI — карточка настроек «Данные удалённых произведений»:
- `widget.Select` с семью вариантами и пояснение под ним;
- при варианте «Своё число…» появляется `widget.Entry` с валидатором 1…36500, сохранение только валидного значения;
- если сохранённое число совпадает с готовым вариантом, выбирается этот вариант.

`Select`, а не `RadioGroup`: семь пунктов на телефоне заняли бы экран. Адаптер D5 читает срок при каждой сверке, поэтому изменение применяется со следующего сканирования.

### D9. API для следующих изменений

```go
func (s *Store) Ensure(root, rel, fp string) (uid int64, err error) // найти или создать (лениво)
func (s *Store) Lookup(root, rel string) (uid int64, ok bool, err error)
```

Таблицы данных (`custom-tags` и далее) добавляются миграциями в этом же пакете.

### Потоки и платформы

- Все методы `Store` потокобезопасны; запись сериализуется мьютексом, как в каталоге. Из UI-потока `Store` не вызывается: сверка идёт в горутине сканирования, удаление — в фоне `Shell.confirmDelete`.
- UI-поток затрагивают только toast восстановления (уже в `fyne.Do`-контексте `SetOnStarted`) и карточка настроек, которая пишет только `Settings`.
- Windows и Android ведут себя одинаково, отличается только ключ папки (D3). Остальные desktop-платформы собираются через `app_desktop.go` (`!android`) так же, как Windows, stub не нужен.
- Сторонних компонентов не добавляется, `THIRD_PARTY_NOTICES.md` не меняется.

## Risks / Trade-offs

- [Разрешение SAF отозвано, а обход возвращает пустой список вместо ошибки] → правило пустой папки не даст пометить сирот; отдельная задача проверяет поведение `storage.SAF.Walk` при отозванном разрешении.
- [Полное пересканирование после обновления (каталог v3)] → однократно, как при любой смене схемы каталога; пишется в журнал.
- [Одинаковые архивы (дубликаты)] → перенос только при однозначном совпадении, иначе запись остаётся сиротой.
- [Пользователь сократил срок и потерял данные] → пояснение в карточке: «Данные произведений, файлы которых не найдены дольше срока, удаляются»; удаление только на успешной сверке.
- [Перевод часов] → срок считается от `orphaned_at` по системному времени; ошибка в пределах сдвига часов допустима.
- [Смена папки на Android отвязывает данные] → записи прежней папки не удаляются и вернутся при возврате к ней; перенос между папками — вне рамок.

## Migration Plan

- Первый запуск новой версии создаёт `user.db` v1 (пустую) и пересоздаёт каталог v3.
- Откат на прежнюю версию: она не знает `user.db` и не трогает его; каталог v3 для неё «чужой версии» и пересоздаётся. Данные сохраняются до повторного обновления.

## Open Questions

- Понадобится ли ручная кнопка «Удалить данные удалённых произведений сейчас»? Не в этом изменении.
