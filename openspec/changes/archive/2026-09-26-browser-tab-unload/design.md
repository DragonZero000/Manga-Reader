## Context

`BrowserEngine` (Kotlin `object`, живёт весь процесс) держит `tabs: MutableList<Tab>`. У `Tab` поле `val session: GeckoSession` открывается при создании вкладки и закрывается только при её закрытии. `BrowserActivity` при `onStart` подключает активную вкладку к `GeckoView` (`setSession`), при `onStop` отключает её (`releaseSession`). Остальные сессии всё это время остаются открытыми. У каждой свой процесс контента Gecko, около 165 МБ по замеру пользователя.

Замер пользователя на S25 Ultra: без браузера 230 МБ; браузер со стартовой страницей 350 МБ; 3 вкладки 850 МБ.

Нужный API есть в GeckoView 156 (проверено `javap` по aar):
- `ProgressDelegate.onSessionStateChange(session, SessionState)` — актуальное состояние (история, адрес, прокрутка);
- `GeckoSession.restoreState(SessionState)`, `purgeHistory()`, `setActive(boolean)`, `setPriorityHint(int)`, `close()`, `isOpen()`;
- `ContentDelegate.onKill(session)` — система завершила процесс вкладки; `onCrash(session)` — процесс вкладки упал.

Платформа только Android. Go-код не меняется. На Windows браузер — отдельный процесс Firefox, изменение его не касается.

## Goals / Non-Goals

**Goals:** в браузере загружены не больше двух вкладок; после ухода из браузера загружена только активная, в неактивном состоянии; выгруженные и убитые системой вкладки восстанавливаются с историей; загрузки не прерываются; замер памяти до и после.

**Non-Goals:** отдельный процесс для браузера, сохранение вкладок на диск, настройки политики.

## Decisions

### D1. Модель вкладки

```kotlin
class Tab(session: GeckoSession?) {
    var session: GeckoSession? = session   // null — выгружена
    var state: GeckoSession.SessionState? = null  // из onSessionStateChange
    var downloads = 0                      // идущие загрузки с этой вкладки
    var lastUsed = 0L                      // SystemClock.elapsedRealtime()
    // title, url, canGoBack, canGoForward, progress — как сейчас
    val loaded get() = session?.isOpen == true
}
```

Все обращения к сессии в `BrowserActivity` (`loadUri`, `reload`, `goBack`, `goForward`, закладки) идут через `BrowserEngine.activeSession()`. Эта функция при необходимости сначала восстанавливает вкладку. Прямого `tab.session` вне движка нет.

Альтернатива — держать `SessionState` сериализованным (`toString()`) и восстанавливать через `fromString`. Отклонено: в памяти объект и так небольшой, а сериализация нужна только для записи на диск, это Non-goal.

### D2. Выгрузка и восстановление

```
unload(tab):  loaded? && downloads == 0 && tab не подключена к GeckoView
              → session.close(); tab.session = null      (state остаётся)
restore(tab): tab.session == null
              → s = GeckoSession(); setup(tab, s); s.open(runtime)
              → state != null ? s.restoreState(state) : s.loadUri(url)
```

- `setup` получает сессию параметром, делегаты привязываются к вкладке. События от старой, уже закрытой сессии отбрасываются по условию `session === tab.session`, чтобы запоздавший колбэк не испортил данные вкладки.
- **Восстановление при показе.** `attach()` в `BrowserActivity` вызывает `BrowserEngine.ensureLoaded(tab)` до `setSession`. `select(i)` восстанавливает новую активную и применяет политику D3.
- **`onSessionStateChange`** сохраняет `tab.state` при каждом изменении, поэтому к моменту выгрузки состояние свежее.
- **Текущая страница.** GeckoView не сохраняет в `SessionState` содержимое форм и состояние JS: после восстановления страница загружается заново. Это ожидаемо и так же ведут себя Chrome и Firefox на Android.

### D3. Политика: «активная + последняя»

`enforce()` вызывается после `select`, `newTab`, `onNewSession`, `close` и завершения загрузки:
- пока экран браузера на переднем плане (`foreground = true`): оставить загруженными активную и одну вкладку с наибольшим `lastUsed` среди остальных; остальные выгрузить;
- в фоне (`foreground = false`): оставить только активную;
- вкладки с `downloads > 0` не выгружаются ни в каком случае.

`lastUsed` обновляется, когда вкладка становится активной и когда с неё уходят.

Почему две, а не одна: частый сценарий — переключение туда-обратно между списком (каталог сайта) и страницей произведения. С одной загруженной вкладкой каждое переключение перезагружало бы страницу. Одна лишняя вкладка стоит около 165 МБ, пока пользователь в браузере. После ухода из браузера она выгружается.

### D4. Передний план и `setActive`

- `BrowserActivity.onStart`: `BrowserEngine.foreground = true`; активной вкладке `setActive(true)` и `setPriorityHint(PRIORITY_HIGH)`; `attach()`.
- `BrowserActivity.onStop`: `releaseSession()`; активной вкладке `setActive(false)` и `setPriorityHint(PRIORITY_DEFAULT)`; `foreground = false`; `enforce()`.
- `onStop` срабатывает для «MangaReader» (читалка выходит на передний план), «Назад» (`finish`) и сворачивания. Отдельные ветки не нужны.

### D5. Загрузки

`DownloadManager.start(ctx, response, page, tree, onFinish: () -> Unit)`. Колбэк вызывается ровно один раз по `DONE` или `FAILED` (и при раннем отказе, если папка не выбрана) из потока загрузки. В `onExternalResponse` движок делает `tab.downloads++` и передаёт `onFinish = { main.post { tab.downloads--; enforce() } }` — счётчик меняется только в главном потоке.

Почему защищаем вкладку: неизвестно, живёт ли поток `WebResponse.body` после `session.close()`. Канал загрузки открыт в процессе Gecko для этой сессии. Проверить это надёжно нельзя, а прерванная загрузка архива на 300 МБ хуже 165 МБ памяти. Задача 4.3 проверяет, что загрузка при выгрузке других вкладок не прерывается.

### D6. Процесс вкладки завершён системой

`ContentDelegate.onKill(session)` и `onCrash(session)`: если `session === tab.session`, вкладка считается выгруженной (`tab.session = null`; сессию после `onKill` GeckoView уже не использует, её закрываем). Если вкладка активна и экран браузера открыт, `listener?.onTabsChanged()` запускает `attach()`, и вкладка восстанавливается. Иначе восстановление произойдёт при показе.

### D7. Очистка истории

`clearData("history")`: для загруженных вкладок `purgeHistory()`, как сейчас. Для выгруженных `state = null`: при восстановлении будет `loadUri(url)`, без истории. `onSessionStateChange` после `purgeHistory` обновит `state` загруженных вкладок сам.

### D8. Потоки

Весь `BrowserEngine` — главный поток Android, как и сейчас. Делегаты GeckoView вызываются в главном потоке. Колбэк `DownloadManager` переходит в главный поток через `main.post`, потому что загрузка идёт в своём потоке. Go и `fyne.Do` не участвуют.

### D9. Замер памяти

Сумма PSS всех процессов приложения (`io.github.mangareader.app` и `…:tab*`, `…:gpu`, `…:extension`…) по `adb shell dumpsys meminfo`. Скрипт `scratchpad/mem.sh` суммирует строки процессов приложения в разделе «Total PSS by process». Сценарии замера:

```
M0  приложение, браузер не открывался
M1  браузер со стартовой страницей
M2  3 вкладки (одинаковые тяжёлые страницы), в браузере
M3  3 вкладки → «MangaReader» (через 10 с)
```

Замер «до» делается на текущем коде (задача 1.1), «после» — после реализации (задача 4.2).

## Risks / Trade-offs

- [Переключение на выгруженную вкладку перезагружает страницу: теряются введённые в формы данные и позиция в бесконечных лентах] → держим две вкладки; поведение как у мобильных браузеров.
- [`restoreState` на сайтах с POST-страницами может предложить повторную отправку формы] → поведение Gecko; не обходим.
- [Родительская часть Gecko (~120 МБ) остаётся после выхода из браузера] → известное ограничение; вариант A (отдельный процесс) — Non-goal.
- [Системе не хватает памяти, и она убивает процесс активной вкладки в фоне] → D6, восстанавливается при показе.
- [Запоздавшие колбэки закрытой сессии] → проверка `session === tab.session` в каждом делегате.

## Migration Plan

Данные не мигрируют: вкладки только в памяти. Откат — revert.

## Open Questions

Нет. Итоги замеров M0–M3 «до» и «после» записываются сюда.

### Замер «до» (26.09.2026)

S25 Ultra, сумма PSS всех процессов приложения (`scratchpad/mem.sh`), чистый запуск, сайты: Wikipedia (Manga), MyAnimeList (Top Manga), Reddit (r/manga).

| Сценарий | Всего, МБ | Процессов | Основные |
|---|---|---|---|
| M0 без браузера | 232 | 1 | app 232 |
| M1 одна вкладка (Wikipedia) | 916 | 6 | app 419, gpu 224, tab 127, tab 64, tab 57, crashhelper 22 |
| M2 три вкладки, в браузере | 1592 | 10 | app 441, gpu 396, tab 226 / 118 / 113 / 110 / 56 / 55 / 53, crashhelper 20 |
| M3 три вкладки, «MangaReader» + 10 с | 1264 | 9 | app 363, tab 216 / 118 / 113 / 111 / 57 / 56, gpu 207, crashhelper 20 |

Что видно:
- PSS-сумма выше цифр пользователя (системный экран памяти считает иначе), но сравнение «до/после» делается одним способом.
- Уже одна вкладка стоит ~680 МБ: родительская часть Gecko в основном процессе (~190 МБ), **GPU-процесс Gecko (224–396 МБ)**, процессы контента и `crashhelper`. Два процесса контента по ~55–64 МБ живут независимо от вкладок (заранее запущенный процесс и процесс расширений).
- Вкладки **одного сайта** делят процесс: три вкладки Wikipedia — один процесс на 200 МБ (отдельный замер: 1075 МБ в браузере). Выгрузка даёт выигрыш прежде всего на вкладках разных сайтов; сайты со встроенными фреймами (Reddit) держат по несколько процессов, выгрузка освобождает их все.
- После «MangaReader» память почти не освобождается (−328 МБ, в основном GPU-процесс и основной процесс): все процессы вкладок остаются.
- Выгрузка вкладок не трогает GPU-процесс и родительскую часть Gecko; это ~400–600 МБ, которые освобождает только вариант A (отдельный процесс) — отмечено для решения после замера «после».

### Замер «после» (26.09.2026)

Та же методика; для честного сравнения база переснята на прежней сборке с отметками +60 и +120 с (память Gecko со временем уменьшается сама: GPU-процесс сжимается ~200 → ~95 МБ).

| Сценарий | До, МБ | После, МБ | Разница |
|---|---|---|---|
| M0 без браузера | 236 | 237 | — |
| M1 одна вкладка | 920 | 920 | — |
| M2 три вкладки, в браузере | 1439 (первый прогон 1592) | 1390 | −50…−200 |
| M3 «MangaReader» + 10 с | 1265 | 1075 | −190 |
| M3 + 60 с | 1130 | 974 | −156 |

Журнал движка подтверждает политику: при открытии третьей вкладки выгружена первая (Wikipedia), после «MangaReader» — вторая (MyAnimeList); загруженной осталась только активная (Reddit).

Выводы:
- Выгруженная вкладка другого сайта освобождает ~100–120 МБ (её процесс контента), а не ~165 МБ, как оценивалось по цифрам системного экрана памяти.
- После браузера остаётся ~970 МБ PSS: основной процесс 372 (из них родительская часть Gecko ~135), активная вкладка Reddit 217 + 98 (два процесса — страница и встроенные фреймы), GPU 91, заранее запущенный процесс и процесс расширений 59 + 53, служебные (utility, media, crashhelper) 75. От числа вкладок это уже не зависит.
- Дальнейшее снижение после выхода из браузера (~730 МБ) возможно только вариантом A (браузер в отдельном процессе Android, который завершается при закрытии). Это отдельное изменение; решение — за пользователем.
