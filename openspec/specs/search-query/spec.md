# search-query Specification

## Purpose

Модель запроса поиска по параметрам произведения, описание полей и операций, валидация запроса и контракт индекса поиска.

## Requirements

### Requirement: Параметры поиска
Система SHALL определять фиксированный набор полей, по которым можно искать и сортировать произведения, вместе с типом значения и допустимыми операциями каждого поля:

| Поле | Тип значения | Операции |
|---|---|---|
| `title` (основное и альтернативное) | текст | содержит |
| `tag` (с типом тега) | тег | есть, нет |
| `id` (внешний ID) | число | равно |
| `pages` | число | равно, меньше, больше, между |
| `uploaded` | дата | меньше, больше, между |
| `favorites` | число | меньше, больше, между |
| `scanlator` | текст | равно, содержит |
| `added` (время изменения файла) | дата | меньше, больше, между |
| `size` (размер файла) | число | меньше, больше, между |

Описание полей MUST быть доступно программно (имя, тип значения, операции, возможность сортировки), чтобы UI и парсер запросов строились по нему, а не по жёстко заданным спискам.

#### Scenario: Перечисление полей
- **WHEN** код запрашивает описание всех полей поиска
- **THEN** возвращаются все поля из таблицы с их типами значений и допустимыми операциями

### Requirement: Модель запроса
Запрос SHALL состоять из свободного текста (по названиям), списка фильтров «поле–операция–значение», параметра сортировки (поле и направление) и параметров постраничной выдачи (лимит и смещение). Все фильтры запроса MUST объединяться логическим «И».

#### Scenario: Пустой запрос
- **WHEN** создаётся запрос без текста и фильтров
- **THEN** запрос валиден и означает «все произведения» с сортировкой по умолчанию (`added`, по убыванию)

#### Scenario: Комбинированный запрос
- **WHEN** создаётся запрос с фильтрами `tag есть artist:artist 1`, `tag нет tag:tag 3`, `pages больше 20`
- **THEN** запрос валиден и содержит три фильтра

### Requirement: Валидация запроса
Запрос MUST проверяться перед выполнением. Операция, недопустимая для поля, значение неподходящего типа, диапазон «между» с нижней границей больше верхней, отрицательные лимит или смещение MUST приводить к ошибке валидации с указанием проблемного фильтра.

#### Scenario: Недопустимая операция
- **WHEN** запрос содержит фильтр `title больше 5`
- **THEN** валидация возвращает ошибку, указывающую поле `title` и операцию «больше»

#### Scenario: Некорректный диапазон
- **WHEN** запрос содержит фильтр `pages между 50 и 10`
- **THEN** валидация возвращает ошибку диапазона

#### Scenario: Фильтр по тегу нормализуется
- **WHEN** запрос содержит фильтр `tag есть Artist:"Artist 1"`
- **THEN** значение фильтра хранится как нормализованный тег `artist:artist 1`

### Requirement: Контракт индекса поиска
Система SHALL определять интерфейс индекса со следующими операциями: добавление или обновление галереи, удаление галереи по ключу, поиск по запросу с возвратом упорядоченных ключей и общего числа совпадений, получение подсказок тегов по необязательному типу и префиксу имени со счётчиком галерей. Приложение MUST использовать рабочую реализацию интерфейса (индекс в памяти); пустая реализация остаётся для тестов. UI MUST зависеть только от интерфейса.

#### Scenario: Рабочий индекс
- **WHEN** приложение запускается и сканирует библиотеку с `example.zip`
- **THEN** поиск через интерфейс индекса находит `local:example.zip`

#### Scenario: Пустая реализация
- **WHEN** используется пустая реализация индекса
- **THEN** поиск возвращает ноль результатов без ошибки

### Requirement: Фильтр по тегу любого типа
Фильтр по тегу SHALL допускать пустой тип тега, означающий «тег с таким именем любого типа». При валидации имя тега MUST нормализоваться, а пустой тип MUST сохраняться пустым.

#### Scenario: Тег без типа
- **WHEN** запрос содержит фильтр «есть тег» с типом `""` и именем `Tag 1`
- **THEN** запрос валиден, значение фильтра — тег с пустым типом и именем `tag 1`
