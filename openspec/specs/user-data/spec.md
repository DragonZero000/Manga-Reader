# user-data Specification

## Purpose

База пользовательских данных `user.db`: расположение, миграции схемы, восстановление после повреждения, записи произведений со стабильным идентификатором и отпечатком содержимого, сверка со сканированием и перенос по отпечатку, пометка и удаление сирот, настройка срока хранения данных удалённых произведений.

## Requirements
### Requirement: Файл пользовательских данных
Приложение SHALL хранить пользовательские данные о произведениях в отдельном файле SQLite `user.db`: на ПК — в папке приложения рядом с `library.db`, на Android — в личной папке приложения. `user.db` MUST NOT храниться в папке библиотеки. `user.db` MUST NOT пересоздаваться при пересоздании, очистке или смене версии каталога `library.db`.

#### Scenario: Расположение на ПК
- **WHEN** приложение на Windows запущено впервые
- **THEN** рядом с `mangareader.exe` есть `user.db`, в папке `manga` новых файлов нет

#### Scenario: Каталог пересоздан
- **WHEN** в `user.db` есть запись произведения, а `library.db` удалён и приложение запущено
- **THEN** каталог создаётся заново, запись в `user.db` сохранена

### Requirement: Миграции схемы
`user.db` SHALL хранить номер версии схемы. При открытии базы более старой версии приложение MUST последовательно применить недостающие миграции в одной транзакции; данные MUST сохраняться. Если версия базы новее известной приложению (запуск старой версии приложения), приложение MUST NOT изменять и удалять файл; пользовательские данные в этом запуске MUST быть недоступны, причина MUST записываться в журнал.

#### Scenario: Обновление приложения
- **WHEN** приложение с версией схемы 2 открывает `user.db` версии 1 с записями
- **THEN** база приведена к версии 2, записи сохранены

#### Scenario: Откат приложения
- **WHEN** приложение с версией схемы 1 открывает `user.db` версии 2
- **THEN** файл не изменён, приложение работает без пользовательских данных

### Requirement: Восстановление после повреждения
Если `user.db` повреждён (не открывается как SQLite или не проходит проверку целостности), приложение MUST переименовать его в `user.db.broken-<ГГГГММДД-ЧЧММСС>` (вместе с файлами журнала), создать новую пустую базу и при запуске показать сообщение о том, что пользовательские данные повреждены и сохранены в резервную копию. Если базу невозможно создать или открыть на запись, приложение MUST работать без пользовательских данных и записать причину в журнал. Работа приложения MUST NOT прерываться.

#### Scenario: Мусор вместо базы
- **WHEN** `user.db` заменён файлом с мусором и приложение запущено
- **THEN** рядом лежит `user.db.broken-…` с прежним содержимым, создана новая `user.db`, показано сообщение о повреждении, библиотека работает

### Requirement: Записи произведений
База SHALL хранить для произведения запись с постоянным внутренним идентификатором, папкой библиотеки, путём файла относительно неё, отпечатком содержимого и отметкой «сирота» (время, с которого файл не найден; пусто — файл на месте). Пользовательские данные MUST ссылаться на внутренний идентификатор, а не на путь. Запись MUST создаваться только при первом сохранении пользовательских данных о произведении. Папка библиотеки на ПК MUST учитываться как «папка библиотеки приложения», а не как абсолютный путь; на Android — как выбранная папка SAF.

#### Scenario: Ленивая запись
- **WHEN** библиотека из 300 архивов просканирована, а пользовательских данных ни о каком произведении нет
- **THEN** в базе нет ни одной записи произведения

#### Scenario: Перенос портативной папки
- **WHEN** на ПК папка приложения с записью для `a.zip` перенесена на другой диск и приложение запущено
- **THEN** запись по-прежнему относится к `a.zip`

### Requirement: Сверка после сканирования
После каждого успешного сканирования доступной папки библиотеки приложение SHALL сверить записи текущей папки с найденными файлами строго в таком порядке:
1. записи, файл которых найден, MUST терять отметку «сирота»; изменившийся отпечаток MUST обновляться;
2. новый файл (без записи) MUST получать запись, если среди записей текущей папки, файл которых не найден, ровно одна имеет тот же отпечаток и среди новых файлов с этим отпечатком ровно один; путь записи меняется, отметка «сирота» снимается. При нуле или нескольких совпадениях перенос MUST NOT выполняться;
3. оставшиеся записи, файл которых не найден, MUST получать отметку «сирота» с текущим временем (уже помеченные сохраняют прежнее время);
4. записи с отметкой «сирота» старше срока хранения MUST удаляться вместе с их пользовательскими данными.

Найденным считается любой файл, который увидело сканирование, включая ошибочные и занятые другой программой. Неуспешное сканирование (папка недоступна, нет разрешения, ошибка обхода) MUST NOT менять записи. Если сканирование доступной папки не нашло ни одного файла, шаг 3 MUST пропускаться. Записи других папок библиотеки MUST NOT затрагиваться.

#### Scenario: Переименование при закрытом приложении
- **WHEN** у `a.zip` есть запись, пока приложение закрыто файл переименован в `b.zip`, приложение запущено
- **THEN** после сканирования запись относится к `b.zip` и не помечена сиротой

#### Scenario: Переименование при работающем приложении
- **WHEN** у `a.zip` есть запись, файл переименован в `sub/b.zip`, и одно сканирование видит пропажу `a.zip` и появление `sub/b.zip`
- **THEN** запись относится к `sub/b.zip`

#### Scenario: Дубликаты
- **WHEN** у `a.zip` есть запись, `a.zip` пропал, а появились `b.zip` и `c.zip` с тем же содержимым
- **THEN** запись не переносится и помечается сиротой

#### Scenario: Изменён meta.json
- **WHEN** у `a.zip` есть запись, а внутри архива изменён только `meta.json`
- **THEN** запись остаётся у `a.zip`, отпечаток не меняется

#### Scenario: Вынута флешка
- **WHEN** папка библиотеки недоступна и сканирование завершилось ошибкой
- **THEN** ни одна запись не помечена сиротой и не удалена

#### Scenario: Пустая папка
- **WHEN** папка доступна, но в ней нет ни одного файла, а записи есть
- **THEN** новые сироты не появляются

#### Scenario: Маленькая библиотека
- **WHEN** в библиотеке 2 архива с записями и пользователь удалил один из них в Проводнике
- **THEN** после сканирования запись удалённого помечена сиротой

#### Scenario: Возвращение файла
- **WHEN** запись `a.zip` помечена сиротой 10 дней назад при сроке 1 месяц, и `a.zip` снова появился
- **THEN** отметка «сирота» снята, данные сохранены

#### Scenario: Истёк срок
- **WHEN** запись помечена сиротой 31 день назад при сроке 1 месяц, выполнено успешное сканирование
- **THEN** запись и её данные удалены

#### Scenario: Другая папка
- **WHEN** на Android выбрана папка B, а у папки A есть записи-сироты старше срока
- **THEN** сканирование папки B записи папки A не удаляет

### Requirement: Удаление через приложение
Успешное удаление произведения через меню приложения («Удалить…») SHALL сразу помечать его запись сиротой с текущим временем, независимо от правила пустой папки. Запись MUST храниться в течение срока хранения и MUST переноситься по отпечатку, если файл вернётся (например, из корзины Windows).

#### Scenario: Удалён последний файл
- **WHEN** в папке один архив с записью и он удалён через «Удалить…»
- **THEN** запись помечена сиротой, хотя папка стала пустой

#### Scenario: Восстановление из корзины
- **WHEN** на Windows `a.zip` с записью удалён в корзину и через день восстановлен
- **THEN** после сканирования запись снова относится к `a.zip`, отметка «сирота» снята

### Requirement: Срок хранения данных удалённых произведений
Настройки SHALL содержать выбор «Хранить данные удалённых произведений» с вариантами: 1 день, 1 неделя, 1 месяц, 3 месяца, 1 год, бессрочно, своё число дней. По умолчанию MUST быть выбран 1 месяц. Для расчёта 1 неделя = 7 дней, 1 месяц = 30 дней, 3 месяца = 90 дней, 1 год = 365 дней. «Своё число» MUST принимать целое число дней от 1 до 36500; иное значение MUST NOT сохраняться, поле MUST показывать ошибку. «Бессрочно» MUST отключать удаление сирот. Новый срок MUST применяться при следующей сверке.

#### Scenario: По умолчанию
- **WHEN** пользователь открывает настройки впервые
- **THEN** выбран вариант «1 месяц»

#### Scenario: Своё число
- **WHEN** пользователь выбирает «своё число» и вводит 45
- **THEN** настройка сохраняется, сироты удаляются через 45 дней

#### Scenario: Неверное число
- **WHEN** пользователь вводит 0 или «abc»
- **THEN** поле показывает ошибку, прежний срок сохраняется

#### Scenario: Бессрочно
- **WHEN** выбрано «бессрочно», запись помечена сиротой год назад
- **THEN** после сканирования запись не удалена
